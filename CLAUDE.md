This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read first

`docs/HANDOFF.md` is the portable project memory and the entry point for any new session — it carries the scope decisions, the model facts, the current phase's state, the current backlog, and the next phase's kickoff instruction. Read it before planning work; it is kept short enough to read in one pass, and keeping it that way is part of the job.

Every **merged** phase's full narrative — its owner rulings, review findings, and the lessons behind them — lives in `docs/history/`, one dated file per phase, moved verbatim out of the handoff when the phase closed. HANDOFF §4 keeps one paragraph per phase and points there. Read a history file only when you need that phase's detail; don't read them all.

Two documents are binding, not advisory:

- `docs/superpowers/specs/2026-07-29-heat-treat-erp-design.md` — the approved spec. §3 (non-goals) and §15 (decision log) are the contract.
- `docs/superpowers/plans/2026-07-29-roadmap.md` — the 8-phase build order.

**The owner's prime directive: DO NOT MAKE ASSUMPTIONS.** When the spec and the handoff don't answer a question, ask the owner rather than inventing an answer. A large list of features is deliberately out of scope (scheduling, shop-floor tracking, inventory, order duplication, CAR, and more — handoff §3); do not re-add them because they seem like obvious ERP functionality.

**The E2E suite and the demonstration dataset cannot share the dev database, and `test:e2e` refuses
rather than discovers that at flow 20** (#167a). Almost every ambient-state assertion in the suite is
scoped to the flow's own fixtures — `invoice-shipped-order` counts only ITS surcharge row, and
`boardRow` (`e2e/lib/orders.mjs`) matches the board's order-number CELL, never "any cell holding
these digits" (an order whose Weight cell read `1200` collided with order #1200 for real). But
`close-month-end`'s figures are global by definition — a month-end close IS a plant-wide
reconciliation — so `run.mjs` reads the dev DB's ambient state BEFORE flow 1 and refuses the whole
run by name in about a second. **FOUR conditions, each one an assertion that flow itself makes about
the whole plant**: a `ClosePeriod` already covering the current month, an OPEN receipt batch carrying
a payment dated in it, a non-zero continuity variance, and a GL-export readiness gap naming a row the
run does not own (only those — the `plant-default` gaps are the run's own to fix, and an unfiltered
list refuses every pristine dev DB, where `arGlAccountId` is null by definition). A FIFTH reason is
`preliminaryReport` REFUSING to answer: it throws 409 on a skipped month, which the demonstration
dataset produces the moment the calendar rolls past its seed month, and unwrapped that surfaced as an
`execFileSync` "Command failed" — the opaque failure this exists to delete, one step earlier. The
policy is the pure leaf `e2e/lib/preflight.mjs` (the `warmupRefusal` shape, pinned in
`tests/e2e-harness.test.ts`); the evidence comes from `db-fixtures.ts`'s read-only `preflight`
command, which calls the close/export services' OWN reads so the check can never drift from the
assertions it hoists. **Do not widen it** — a pre-flight that over-refuses is one people disable. The
recipe it prints is `npm run db:reset`; the way back to the dataset is `docs/manual/dataset.md`.

**`db:reset` CANNOT prove it is not pointed at production, and says so instead of pretending.**
`current_database()` cannot discriminate the case that matters — production's database is also named
`erp`, which is exactly why `practice-mode.ts`'s mirror of this guard works and this one does not —
and compose publishes the db service on `127.0.0.1:5432`, so on the production host the production
database IS `localhost:5432/erp`. So beyond the two identity checks it refuses `NODE_ENV=production`
outright and **confirms before it truncates**: the database name typed back at a TTY, `--yes` (or
`DB_RESET_CONFIRM=yes`) where there is no terminal to ask at, which is why the harness's recipe prints
both forms. No "looks like production" heuristic was shipped and none should be: every candidate
refuses a well-used dev database, which is the database people reset. The URL-shape half is the pure
leaf `src/lib/dev-db-guard.ts`, shared by all four destructive/read scripts (it was four hand copies
and they had drifted); it has no override flag, deliberately.

**A green flow must be green for the right reason, and static sweeps enforce that** (`e2e/lib/flow-lint.mjs`,
run in `run.mjs` before flow 1 and swept centrally in `tests/e2e-harness.test.ts`). An order-board row
locator must be `boardRow`, never one built off `page` and filtered by an order number. Absence is
asserted with `assertNeverVisible` (`e2e/lib/ui.mjs`), never `assert.rejects(...waitFor(...))`: that
passes on ANY rejection, so a strict-mode violation — two matching elements — makes "this must not be
on screen" report SUCCESS while it is on screen twice, which `void-order` shipped for real. And a flow
assertion is written with `node:assert`, never `throw new Error` (#193, `findPlainErrorThrows`): a
plain Error carries no `ERR_ASSERTION` code, so `classifyFailure`'s override does not cover it and a
stale netFailure launders it into a green retry. Every detector over-matches and fails CLOSED, the
`findRawApiMutations` rule: the escape hatch is the helper (or `assert.*`), never a comment. **The
sweeps read `e2e/flows/**` AND `e2e/lib/**`, minus the two detector modules** (#192) — the file set
lives once in `e2e/lib/suite-sources.mjs`, read identically at both enforcement points, because
`boardRow`/`assertNeverVisible` themselves live in `e2e/lib/` and a bad line written into a shared
helper is worse than the same line in one flow (every flow calls it). A swept lib helper's docstring
therefore describes anti-patterns in prose, never quotes them (the `board-search-scan` precedent), or
it trips its own fail-closed detector. Say "in a swept suite source", not "in a flow file".

**`npm run manual:capture` (`e2e/manual-capture.mjs`) photographs every screen for `docs/manual/` and writes `docs/manual/sweep.md`, a per-screen health report** — own API statuses, console errors, failed requests, real-content-vs-empty-state, load time — exiting non-zero on any console/page error or failed request, so it doubles as a pre-acceptance verification gate. **It also FAILs any screen wider than the capture viewport** (#170): a page can be twice as wide as its window and stay clean by every health signal — which is exactly how the invoice History panel's unwrapped-JSON overflow reached the published manual reported PASS — so `shoot()` measures `scrollWidth` and `statusOf` folds a `scrollWidth > VIEWPORT.width` verdict into FAIL. That is the LIVE gate; `tests/manual-artifacts.test.ts`'s width pin is the committed-bytes backstop, and the two share the same strict comparison so they cannot disagree. It enumerates routes from `src/app/**/page.tsx` (never a hand-list) and discovers ids for the dynamic ones from the dev DB via the read-only `e2e/lib/manual-ids.ts`. It owns port 3200 so it can never fight `test:e2e` for 3100; `MANUAL_BASE_URL` attaches to a server already running instead. **It captures at `deviceScaleFactor` 1** (#169): the manual declares a full-width figure at 1200px and renders it at 800, so 2× density reached no reader while pushing `manual.html` past the publish ceiling — which is why `img/` used to need an undocumented hand-run of `magick`. Leave `MANUAL_SCALE` alone; `tests/manual-artifacts.test.ts` pins it from the committed PNGs' own IHDR widths. **A shot past `MAX_SHOT_HEIGHT` passes `fullPage: true` ALONGSIDE its `clip`** — a bare clip is resolved against the VIEWPORT, so the clipped branch wrote one viewport while `sweep.md` reported a clip to the cap: a generated report asserting something untrue. **The cap itself is sized by measurement, not taste** — high enough to clear every screen whose height is structure, low enough to cut the two that are tall only because they end in an audit list; its docstring carries the pricing and `tests/manual-artifacts.test.ts` pins it from the committed PNGs' own IHDR heights, so re-sizing it is a decision rather than a preference. **Unlike `test:e2e` it writes NOTHING to the database** — which is exactly why the manual's screenshots must come from it: `test:e2e` creates and then reaps its own dev-DB fixtures, so pointing it at the demonstration dataset would rewrite the very data the pictures are of. Its one unavoidable write, `/orders/new`'s draft autosave, is bounded (it refuses to type at all if a draft banner is already open, and discards only a draft it created itself); opening a template draft is a real mutation and is therefore opt-in behind `MANUAL_OPEN_DRAFT=1`.

**`npm run manual:build` (`scripts/build-manual.mjs`) regenerates `docs/manual/manual.html`** — the single-page, self-contained build of the 14 chapters, figures embedded as `data:` URIs. **Zero dependencies and deterministic** (same inputs → same bytes, so a no-op rebuild is a no-op diff; there is no timestamp in it, deliberately) — an image encoder is the dependency it must never grow (#169 rejected shelling out to ImageMagick for exactly that reason). **Figure sizing lives in `scripts/lib/manual-figure-size.mjs`**, its one local import: the display width is `DECLARED_WIDTH_PX` (1200) when the image is at least that wide, else the image's own intrinsic width. **1200 is the declared-attribute cap, NOT the column** — the rendered column is 800 CSS px (`.content` is `max-width:50rem`), and the attribute exists only to fix the aspect ratio and reserve the space. The rule reads each image's intrinsic width instead of the old `round(intrinsic × 10/24)` — which is `1200/2880` and silently hardcoded the capture scale, so changing `MANUAL_SCALE` halved every figure and anything narrower was shrunk on top of that — and it is resolution-independent **at or above 1200 only**: below it the declared width is the intrinsic PHYSICAL width, which is inherent (an IHDR carries no device scale factor) and reaches no figure today. It also states the 16 MB publish ceiling and warns at 85% of it; if that ever reds, re-capture, never reach for `magick`. Chapter order is derived from the `NN-*.md` filenames AND `README.md`'s contents table, which must agree or the build fails; a figure reference that does not resolve is a **loud build error**, because a silently broken figure is the exact defect this exists to catch. **Run it after any change that alters a screen the manual documents** — the page was hand-built once with no generator, and went stale the first time a control was renamed. **CI now proves that for you**: the `ci` job rebuilds the manual and fails on a non-empty `git diff` of `manual.html` (a fraction of a second, and it goes in the REQUIRED check rather than a free parallel job, because a docs-rot guard that cannot block a merge is the rot again), while `tests/manual-artifacts.test.ts` pins the 16 MB ceiling and the capture scale from the committed artifact with no browser. The markdown subset is hand-rolled and deliberately omits `_underscore_` emphasis and `~~strikethrough~~`: permission actions (`override_credit_hold`) and a quoted audit diff (`~~OPEN~~ → SHIPPED`) appear bare in the chapters and would otherwise be mangled.

## Architecture

**Request path.** Every API route is `handle(async (req) => ...)` from `src/server/http.ts`. `handle` resolves the session from the `erp_session` cookie, runs the handler inside an `AsyncLocalStorage` actor context (`src/server/context.ts`) so the audit layer knows who acted without threading a user parameter through every call, and converts `HttpError` and `ZodError` into clean JSON responses. Anything else escaping a handler is a bug, not an expected failure.

Handlers stay thin and follow a fixed shape — authorize, parse, delegate:

```ts
export const POST = handle(async (req) => {
  mustCan(requireUser(), "admin", "edit");   // requireUser() is no-arg and synchronous (http.ts) — it reads the actor from context
  const { name } = z.object({ name: z.string().min(1) }).parse(await req.json());
  return NextResponse.json(await createRole(name));
});
```

Business rules live in the services under `src/server/*.ts`. React components hold no business logic.

**Permissions** (`src/server/permissions.ts`, constants in `src/lib/permission-constants.ts`). 12 areas × view/create/edit/delete, plus 13 named special actions (count them in `SPECIAL_ACTIONS`, never from memory — this line said "10" for several phases while the array grew). Resolution order is DENY override → GRANT override → role grant → deny. Use `mustCan(user, area, action)` / `mustDo(user, special)` in routes; `can`/`canDo` return booleans for UI gating.

**Audit** (`src/server/audit.ts`). Every mutation goes through `auditedCreate` / `auditedUpdate` / `auditedSoftDelete` — `settings.ts`'s direct write is the one sanctioned exception. Phase 3 added two more: the order-draft service (`order-drafts.ts`, pre-entity scratch — spec-authorized, sweep-allowlisted) and `allocateNumber`'s counter bump (the consuming entity's own create entry is the audit trail). Phase 8B added `practice-seed.ts`'s `reseedSingletons` (sweep-allowlisted): a truncate/re-seed to a valid baseline is a **reset, not an acknowledged history** (§5.3), the same as `truncateAll`'s own long-standing unaudited re-seed it was lifted from. `auditedUpdate` snapshots before and after, and `SNAPSHOT_INCLUDE` decides which relations are pulled into those snapshots. **Adding an auditable entity is FOUR edits, not two: `AuditableModel`, `SNAPSHOT_INCLUDE`, and — when the model is a child SECTION of a page carrying a History panel — an `AUDIT_CHILDREN` entry (`src/lib/audit-children.ts`, whose header carries the rest) plus `invalidateHistory()` on the success path of every client mutation that writes it.** The fourth is not optional: a registry entry makes the panel ADVERTISE that child's history, and without the wiring the panel then goes stale on exactly the edits it just started showing (`#14 item 1`'s contract, which predates #153 and covered the part sections only). **Two sweeps in `tests/audit-children.test.ts` enforce the fourth edit, and they are not interchangeable (#158).** `INVALIDATION_SITES` is keyed by registered CHILD entity and reaches section components that mount no panel of their own; it asks for **at least one** wired file per entity, never all of them, so a SECOND page writing an already-covered child is invisible to it — which is how `admin/surcharges` shipped live, mounting a `surcharge` panel and clearing `customerSurcharge` overrides with no invalidation at all. The page-keyed sweep beside it is the complete census: **a client file that mounts a `<HistoryPanel>` — or renders a component that does — and issues a mutating request must import and call `invalidateHistory()`** — derived by walking `src/`, never hand-listed, with the panel-mount set cross-checked against the import set and the mutation detector deliberately over-matching so it fails CLOSED. **Both halves of that census are PARSED, never pattern-matched (#188)**: the consumers come from a `.tsx` value-import graph walked to a transitive closure (type-only edges excluded — a child section type-imports its panel-mounting parent, so counting those folds the sections in backwards), and "calls `invalidateHistory()`" is a `CallExpression` on the bare identifier. Do not add a regex back to either. A panel page that genuinely does not mutate is an allowlist **entry with a reason**, never a silent absence. **Neither sweep reaches a SECTION that mounts no panel and writes a non-registered entity** — `CertificationsSection`'s cert writes are the documented case (owner ruling 2026-08-21: child documents stay off the parent panel), recorded at that code because nothing mechanical will re-raise it. Omitting the relations means changes made through join tables never show up in history; omitting the registry entry means that section's edits never show up on its parent's panel at all, which is what #153 fixed for pricing, specs, addresses and the rest. `readAuditWithChildren` walks that registry and **`readAudit` stays EXACTLY as it is** — the exact-match primitive 40-odd call sites pin; never fold the union into it. **Child-id resolution must NEVER filter `deletedAt`**: the child's own *delete* entry is the row the panel most needs, and an intermediate hop soft-deleted since (a price row carrying breaks) must not take its children's history with it — pin it with a delete-row-specific assertion, never a count, which a live-rows-only walk still passes. The union read is capped and the panel STATES the truncation, so the single-record route branch answers `{ rows, hasMore }`, not a bare array — every consumer reads the envelope and finds the parent's own row by `entity`, not by position. `redact()` scrubs keys matching password/token/secret/signatureImage recursively, but treat it as defense-in-depth: don't hand a secret-bearing payload to the audit layer in the first place.

**Row locks, not isolation levels, guard cross-transaction invariants.** `workingRevision` and `lockCurrentRevision` (`part-process-steps.ts`) and `claimOrder` (now in the leaf module `src/server/order-locks.ts`) all claim their row with `SELECT … FOR UPDATE` before reading the state they act on. The lock works at ANY caller isolation; making one side Serializable is never a substitute (Postgres only serializes transactions that are all Serializable). Order mutations, traveler prints, revision cuts, and every shipment/cert mutation all serialize through these claims — do not bypass them with a bare read, and do not "simplify" a claim into a plain `findFirst`. **STANDING INVARIANT (Phase 6, the period-lock's shape):** an order save that links a quote line runs **Serializable and reads that quote line inside the same transaction**, SSI-paired with the quote service's own Serializable line-drop/delete writers (§5.14) — downgrade either side to Read Committed and the guard breaks silently (SSI tracks only all-Serializable transactions); the dangerous-direction test in `tests/quote-links.test.ts` pins the order-save side (it asserts the surviving order line's `quoteLineId` is **null** — the data outcome, not a status code; since #115 the save retries rather than 409ing, and a Read Committed downgrade shows up as a link onto the dropped line).

**Every caller that allocates a number retries — `retryAllocation`, not a bare Serializable transaction (#115).** `allocateNumber` claims its counter with `SELECT … FOR UPDATE`, so under Serializable the loser aborts with 40001 the instant another allocation commits. Measured: of N concurrent allocations exactly ONE succeeded and N-1 failed outright. This is **not** avoidable by allocating earlier — `allocateNumber`'s own first statement is a write (`INSERT … ON CONFLICT DO NOTHING`), which fixes the snapshot before the claim — and not by a Postgres sequence, because "consumes no number when the save fails" is a pinned contract. So the eight allocating entry points (`saveNewOrder`, `saveNewShipper`, `reverseShipperInTx`, `printBol`, `createCredit`, `createBatch`, `createQuote`, `exportClose`) wrap their transaction in `retryAllocation` (`db-errors.ts`), INSIDE `withDbErrors` and OUTSIDE `$transaction` so each attempt gets a fresh snapshot. N concurrent allocations need up to **N attempts** (one commits per round), hence `ALLOCATION_TRIES = 10` rather than the default 5 — 5 covers the documented 1–5 users with zero margin. **A new allocating caller must do the same**, and a path that takes an injected `tx` must NOT retry (a caller's aborted transaction cannot be re-run from inside it). **Tests for any of this must set Serializable explicitly** — vitest's default Read Committed merely blocks and re-reads, which is what hid this for five phases.

**A read taken from inside a transaction must run ON that transaction (#60).** A service read helper that defaults to the top-level `prisma` singleton executes on a DIFFERENT connection, so a caller inside a Serializable transaction gets a read outside its snapshot *and* outside its read-set: a concurrent edit to the row it read is invisible to SSI (no 40001, no retry), and several such reads can tear across a mid-flight change. `listPartPrices` did this per order line inside the invoice transaction for five phases. The shape is `listAddresses`'/`readShipperDetail`'s — a trailing `db: Prisma.TransactionClient = prisma` parameter — and **the transactional caller must pass its `tx`**; the default exists for the un-transactional callers, not as an opinion. Test it deterministically rather than racing: a row written inside the caller's transaction is visible to the read only if the read is genuinely on that transaction.

**Multi-order writes claim through `claimOrdersInOrder`, one sorted statement.** A write touching several orders (a multi-order shipment save, its void, its child replaces) must claim them via `claimOrdersInOrder(tx, orderIds)` (`order-locks.ts`): deduplicated, ascending, and locked in ONE `SELECT … WHERE id = ANY(…) ORDER BY "id" FOR UPDATE` statement. A loop of per-row `claimOrder` calls — even a sorted loop — reopens the ABBA deadlock window between statements; the single ordered statement is the shape that closes it (`EXPLAIN` shows `LockRows` above `Sort`). Never add a second, differently-ordered claim path. **The guarded state must live on, or be locked with, the claimed row**: if the invariant you check after a claim lives on a different row (a cert's or shipper's `deletedAt`), lock that row too, uniformly after the order claims — a Serializable snapshot fixed before the claim will otherwise re-read stale state, and SSI only saves you by accident (Phase 4's whole-branch review found print-vs-void completely unprotected this way).

**Deletion is always soft** (`deletedAt`), with active flags for hiding. Hard deletes only in tests. Unique columns on soft-deletable models are unique **only among live rows** (a partial index filtered on `deletedAt IS NULL`), so re-using a deleted code creates a genuinely new row with its own id and its own audit history — there is no revival-on-create, and adding one back is a regression. **Never `findUnique`/`upsert` on such a column**: the generated client still types it unique, so both compile, and `findUnique` silently returns the deleted row. Use `findFirst({ where: { code, deletedAt: null } })`. `tests/partial-unique-sweep.test.ts` enforces both halves. A deliberate set of columns stays plain `@unique` on soft-deletable models — allocation-only document numbers (`Order.orderNumber`, `Invoice.creditNumber`, `Quote.quoteNumber`, …) and the `clientRequestId` idempotency keys — because voided/discarded rows keep them forever and they are never re-entered: a discarded draft must never free a number a customer already holds on paper, and handing an idempotency key back to a retry recreates the duplicate it exists to stop. **The census is the `ALLOWED` set in `tests/partial-unique-sweep.test.ts`**, each entry carrying its reasoning at the code — this file deliberately stopped enumerating them (its "six columns" tally had gone stale twice, #236); do not convert any of them to partial-unique. **`Cert` has no unique column at all and adds no sweep exemption** — a cert carries no number of its own (spec §3.19; its label is its order number + scope instance), and one-live-cert-per-scope-instance is service-enforced under the order claim, not indexed (Postgres treats NULLs as distinct, so no index could express it). Do not "fix" either by adding a column.

**Shipper children and cert requirements snapshot what they print (snapshot + release, owner rulings 23–24, 2026-08-06).** `ShipperLine`/`ShipperContainer`/`ShipperSerial`/`CertRequirement` carry snapshot columns (part number/name/description + ordered totals; container type/customer id; serial/description; line position + part identity) captured at save/seed time, and their FKs to the order-side rows are nullable `ON DELETE SET NULL` — order corrections (`removeLine`, `replaceContainers`, `replaceSerials`) must never be blocked by a shipment or cert reference. **Every code path that creates one of these child rows must populate the snapshot columns** (NOT NULL where the paper needs them), and then **the read convention SPLITS by document**: shipment reads go live-join-first with snapshot fallback (`toDetail` in shippers.ts — a shipment is still being edited), while a cert requirement reads its SNAPSHOT unconditionally (`toCertDetail` in cert-results.ts; the Phase 4 round-4 ruling — a cert is frozen at seed, so a later part rename must not shift a seeded certification's identity, and "fixing" it back to the shipment convention reintroduces the exact regression round 4 removed). Released rows (null FK) render read-only in the shipment grids, and shipper-side replaces preserve them (delete only rows with a live FK). Don't "simplify" the shipper fallback away, and don't re-tighten the FKs.

**An invoice is frozen paper — its snapshot columns are read UNCONDITIONALLY, the opposite of the shipment grids' live-join-first (ruling 24's refinement, P5A spec §5.4).** `Invoice`/`InvoiceLine`'s identity and pricing fields (customer name/address, part number/name, GL account name, price fields) are never re-joined to their live source at read time — a part rename, a step-code rename, or a surcharge rate change must never rewrite an invoice that has already been raised. This is deliberately the opposite choice from the SHIPPER live-join rule directly above (the cert requirement read already makes the same frozen-paper choice as the invoice): a shipment is still being edited, so it live-joins with a snapshot fallback for released rows; an invoice is not being edited once its lines are written (draft edits replace the whole line array — §5.5 — they don't patch a live join), so there is no fallback branch to reach for. `invoice-guards.ts` is a dependency-free LEAF, the `order-locks.ts`/`errors.ts` precedent — joined in Phase 6 by `quote-links.ts`, which states the §5.2 eligibility rule ONCE for order entry, the quote close warning, and the part page (Phase 4 lesson 3: pull a cross-module question into a leaf *before* the import cycle exists, not after it crashes at module-evaluation time) — `orders.ts` and `shippers.ts` need to ask "does a finalized invoice cover this order?" without importing `invoices.ts`, which imports both of them. It holds only `finalizedInvoiceFor`/`finalizedInvoicesFor` (read on the caller's own claimed `tx`) and `invoiceBlockMessage`; it throws nothing itself and checks no permission — every caller reads the guard under its own order claim and raises its own `HttpError`, so this file stays importable from anywhere without dragging a permission or service graph behind it. **While a draft, though, a `MANUAL` line is an OVERRIDE, not an addition (owner ruling 2026-08-17, #61):** `recalculateInvoice` pairs each manual line to the derived line sharing its order-side identity (`overrideKey`) and substitutes it into that line's SLOT — regenerating the twin alongside it is a double bill — while a manual line matching nothing rides at the end (§5.5). **The step-exact identity is not sufficient on its own**: a derived operation can come back under a step code the override does not name — the tier-3 "needs price" line carries none, and an operation's part price can be retired and re-added under a different code (the step-code ROW cannot be soft-deleted under a live override: `assertLineRefs` 400s first). So an unmatched OPERATION override falls back to its ORDER LINE, and **only onto an operation that has APPEARED SINCE** — one already carrying its own derived line is a sibling, not the thing this override replaced, and re-homing onto it trades the double bill for an under-bill that erases that sibling from the paper. It covers every qualifying operation if it carries no step code, exactly one if it does; when nothing qualifies it rides as an addition where the operator can see it. Both misses were review findings, in successive rounds, on the same fallback. Tax recomputes over the FINAL set (`taxOnLines`, whose taxable-kind list is shared with `priceOrder` so they cannot drift) at **both** seams — `replaceInvoiceLines` as well as `recalculateInvoice`, since Save and Recalculate are independent actions and finalize freezes what it finds — and a manually overridden TAX line is left as typed. There is deliberately no revert control: remove the row, save, recalculate. **Finalize refuses an EMPTY line set, never a $0 total** — a warranty or no-charge rework is real paper; zero lines made the `needsPrice` check vacuous and stranded the order at INVOICED (#63). **The invoice also freezes the NUMBERS behind `termsName`** (`termsDiscountPercent`/`termsDiscountDays`, written at finalize beside `dueDate`, INVOICE-only): the early-pay discount read the customer's CURRENT terms, so reassigning a customer rewrote what invoices already in their hands were worth, both ways (#79). Read them through `issuedTerms` and add NO fallback to the live relation — a fallback is how the retroactive read creeps back in — and remember there are TWO read sites, since `applyPayment` caps the DISCOUNT line independently of what `discountAvailable` offers. **Adding a frozen column means BACKFILLING existing paper** in the same migration, or the fix silently withdraws something the shop has already promised in writing.

**Document templates are config-consumers; publish resolves by immutability, not by locking (Phase 7).** Every one of the eight document types (traveler, shipper/MOS, BOL, cert, invoice/credit, statement, quote) is a data-driven template. The single source of truth per type is its **template contract** (`src/lib/template-contracts/`, client-safe — the editor imports it): ordered sections/fields with stable keys, default labels, removable/column flags, text blocks, and the format-knob surface. The zod config schema is generated from the contract, the editor renders from it, and each `build<Doc>Definition(data, config)` consumes a validated `TemplateConfig` — **a template can only re-arrange, re-label, restyle, show or hide what the data layer already collects; it can never add a data source**, so every snapshot rule (frozen invoice, live-join-with-fallback shipper/cert) holds for free. **Locked elements (§5.6):** the traveler's typed step fields and its barcode cannot be hidden — the contract marks them non-removable, the editor shows them locked-with-reason, AND the config validator refuses a config that hides them (defense in depth, not editor-only); the builders also carry a `completeSections`-based belt so a section/field entry OMITTED past the validator still renders. **The §5.3 default backfill:** the builders' hardcoded values live as `DEFAULT_CONFIG` TS constants (the canonical copy) — `validateConfig` backfills any knob a stored version predates, so an old version keeps rendering identically, which is why **contracts evolve additively only** — "additive" is a semantic test (every stored config must stay valid AND render the same paper), and some additive-LOOKING changes fail it (a new visible column, a non-removable field in a hideable section, a changed contract default — stored configs pin only what they explicitly store, so every default is live at print): read the `template-contracts/types.ts` header (#103) first. `truncateAll()` re-seeds the eight "Standard" templates from those same constants, and a drift-guard test asserts the seed migration's SQL literal deep-equals them per type (three copies — TS constant, seed SQL, test-re-seed — kept in step by the guard; never let them drift). **Publish-by-immutability (the load-bearing concurrency call, §5.1):** a `PUBLISHED` `DocumentTemplateVersion` is immutable and never deleted, and publish commits the version's status flip and the template's `publishedVersionId` pointer move atomically. Prints resolve `publishedVersionId` under their OWN claimed transactions and are correct at ANY isolation **without locking the template row** — any committed pointer a reader follows yields a complete published config, drafts can never print, and `StoredDocument.templateVersionId` stamps exactly which version produced the paper. A print racing a publish may legitimately render the prior published version — "from that moment" means commit order (accepted by design). **Do not add a template-row claim to any print path.** Template MUTATIONS are the opposite: each claims the `DocumentTemplate` row via `claimTemplate` (the `claimQuote` shape) FIRST at default isolation; `setDefault` claims every live template of the docType in one ordered statement (the `claimOrdersInOrder` rule). Per-customer assignment resolves nearest-live-ancestor → type default through the ONE shared `resolveAssignment` walk (`template-assignments.ts`) that drives both print AND the customer-page picker — never reimplement the walk.

**Settings** (`src/server/settings.ts`) is a typed zod registry validated on both read and write, guarded with `Object.hasOwn` against prototype keys. **Phase 7 retired the four standing-text keys** — `cert_statement`, `shipper_liability_text`, `quote_intro_text`, `quote_liability_text` are template text blocks now (edited in place per template, migrated by `20260813120000_retire_standing_text_settings`); the print paths inject the resolved config's block at the same data seam that once read the Setting. `company_name`/`company_address`/`company_phone` stay (identity, not layout). Do not re-add a retired key: `getSetting` is typed to `SettingKey`, so a stale reader would not compile.

**The period lock (Phase 5C).** A month's open/closed state is a *predicate* (an un-closed month has NO `ClosePeriod` row), so it can't be guarded by a `SELECT … FOR UPDATE` on a row. Both `closePeriod` and `assertPeriodOpen` take a per-`(year,month)` transaction advisory lock (`pg_advisory_xact_lock`, `period-locks.ts`); and — the load-bearing part — the close AND every posting mutation (finalize/unlock/createCredit/postBatch/voidPayment/applyPayment/applyCredit/writeOffInvoice/voidApplication) run **Serializable**, so Postgres SSI aborts the posting-vs-close phantom cycle. The close retries on the serialization/unique conflict (`retryOnSerializationConflict`, `db-errors.ts`) rather than dropping isolation. **STANDING INVARIANT: if any posting mutation is ever downgraded to Read Committed, the period lock silently breaks** (SSI only tracks all-Serializable transactions) — the dangerous-direction test in `close-periods.test.ts` guards this. A plain `findFirst` is not a guard. `postBatch` (a batch can span months) locks its distinct months in ascending order (the `claimOrdersInOrder` rule for advisory mutexes). **Not everything in `period-locks.ts` locks, since #157:** `closedMonthsForDisplay` is a batched, LOCK-FREE read for **display and refusal wording only** — a page asking "is this month closed?" on every render must not take the month's advisory lock, or every customer-page view serializes behind a running close. It is one careless import from breaking the invariant above, so it is pinned twice: a held-lock test proving `assertPeriodOpen` still blocks while it answers, and an **allowlist of its call sites** (`tests/period-locks.test.ts`) that makes a third caller a decision rather than a convenience. Before a mutation you want `assertPeriodOpen`, always. **Recognition basis is `finalizedAt`, not `invoiceDate` (owner ruling 8):** an invoice counts in the month it is finalized, so `finalize` guards the finalize date (≈`todayDateOnly()`) and `unlock` guards the invoice's own `finalizedAt` — guarding `invoiceDate` would let unlocking a July-dated/Aug-finalized invoice silently change August's frozen figures while only checking July (the leak this lock exists to close). `createCredit` guards its raise date (a DRAFT credit recognizes nothing until finalized). The close's dangerous-direction test therefore closes **today's** month.

**The GL-export delta (Phase 5C).** Postings live in an append-only `GlPosting` ledger keyed on `(sourceType, sourceId)`; the delta is computed **strictly per-period** (never cumulative — the period lock keeps a closed month stable, and cumulative bounds would double-post when months export out of order). Finalized invoices/credits are scoped by **`finalizedAt`** (owner ruling 8, matching the close roll-forward and 5B's aging) over the **half-open** `[monthStart, nextMonthStart)` interval (`finalizedAt` is a `DateTime` with a time-of-day — an inclusive `lte monthEnd`-at-midnight would drop a last-day finalize); payments/applications stay `receivedDate`/`appliedDate` inclusive. Readiness must refuse an export for **every** account-bearing non-`TAX` invoice line lacking a GL account (freight/charge/cert too, not only step-code/surcharge), and `exportClose` asserts Σdebit = Σcredit before persisting. **The exported file and posting register are a SUMMARY** — one line per `(account, side)`, debits/credits summed (owner ruling 9, `aggregateLines`) — while the per-event `GlPosting` rows stay UN-aggregated (the ERP-side detail + delta driver); do not de-aggregate the file or aggregate the ledger. Nothing is cached on `Invoice`/`Payment`/`Application`; balances derive live.

**Figures shown together must be READ together.** When one screen prints a total above a table that is supposed to explain it, both come from ONE read-only RepeatableRead transaction — `customerReceivablesSummary` threads its `tx` into `customerOwnAgingRow` and `openItemsForCustomer` (#83), the `agingReport` precedent. Reconciliation is the whole point of such a pair, so it must not depend on two autocommit reads landing on the same side of a commit. The other half of that rule is compositional: the table has to list every KIND the total counts — open invoices, open credit memos AND on-account cash, the last two negative — or the number above it cannot be arrived at from the rows in it.

**The UI fetches in effects BY RULING (#31, 2026-08-18), and the stale-load discipline is a family of client-safe leaves in `src/lib/`.** `react-hooks/set-state-in-effect` stays off permanently (the rationale block in `eslint.config.mjs` is the decision record; spec §15 has the row). The discipline the rule cannot see: every fetch-into-state gates BOTH landings on a `use-latest.ts` ticket taken before the await (a superseded rejection must not clobber current state either — the F7 rule), or the effect-scoped `let stale` cleanup flag where the fetch is keyed by an effect dep. `save-scope.ts` (the #3/#15 fix) guards pages whose saves apply optimistically at CALL time, outside their per-key queue: the epoch is captured BEFORE the settle-wait (the park is itself a save window), and rollback reloads are fired detached — awaiting from inside the settling save deadlocks. `drain-queue.ts` guards the mutation-gate detail pages' §5.13 rollback loads: it drains per-key **request-settled signals registered at dispatch, never queue chain tails** — a chain tail settles only after its own catch, so tail-draining deadlocks two concurrently-failing keys (reviewer-reproduced; a network blip during two blur-saves bricked the page's save surface). Cross-component staleness uses the module-level listener-Set invalidation idiom (`invalidateBackupBanner`/`invalidateSetupBanner`; the setup banner refetches only when it currently renders something — the argon2 cost ruling). Refs that feed queued runs (`rolesRef`/`rowsRef`/`codesRef`) land **applied-monotonic** via `makeMutationGate.accept` on the load ticket, never by arrival. `use-edit-guard.ts` (#149 + three Codex rounds, the session FIXPOINT) protects the field under the cursor: every set-from-server routes through `applyPayload`/`applyRows(collection, …)`, which capture an **immutable focus session** once at dispatch, note the payload into that same identity, and return a PURE setState updater closed over it — never read or write live focus state inside an updater (React defers, rebases, and double-invokes them; live-session reads are event-handler-only, and the leaf header documents the one accepted residual). All of these are pure leaves with deferred-driven vitest suites — extend those, don't hand-roll a new gate shape.

**Reports are pure reads (Phase 8A).** The `/reports` section and the `reports` permission area are live: a client index page driven by the client-safe `report-registry.ts` catalog (each entry gated on its OWN source area, so a homed cross-area report — the invoice register, A/R aging — hides for a caller lacking that area's view), the native reports (backlog, shipped, turnaround, sales, payments, comparison scoreboard), and the two homed entries. Every native report is the **five-part shape** cloned from A/R aging — a pure-core service in `src/server/reports/`, a shared `query.ts` filter parser, JSON + Excel-`export` routes that reuse it (so the table and its file can never disagree about a filter), and a `"use client"` UI. A report **never claims, audits, or runs Serializable** — it may only read (the main spec §12 reads-never-mutate rule); do not add a lock or an audited write to one. It MAY, when a single figure is assembled from several reads that must agree, wrap those reads in ONE read-only **RepeatableRead** transaction (the `aging.ts` `agingReport` precedent; the scoreboard's order-count/shipped/invoice trio does this, threading the tx client through `reportShipped(filter, db)`) — still a pure read, still not Serializable. Financial reports read the **frozen invoice snapshot** (never re-joining live parts/prices) and recognize on **`finalizedAt`** (Sales, matching the close/aging basis) — the one deliberate exception is the comparison **scoreboard**, a Visual-Shop parallel-run eyeball that counts invoiced $ by **`invoiceDate`**.

**Practice copy & first-run onboarding (Phase 8B).** The app ships as a **separate practice copy** (its own `erp_practice` DB + an `app-practice` compose service on port 8080 under a `practice` profile) — never an in-app toggle. **`practiceMode()` (`src/server/practice-mode.ts`) is the single source of practice-vs-production**, resolved **authoritatively from the database identity** (`SELECT current_database() = 'erp_practice'`, memoized per process), with `PRACTICE_MODE` only corroborating — a loud throw on the dangerous mismatch (env says practice, DB is prod). Every consumer reads this one helper: the **banner** (the now-`async` root layout `app/layout.tsx` mounts it above `Shell`'s `/login` and me-null early returns; the flag is NEVER read in a client component — §8), the **watermark** (`render.ts`'s `stampPractice`, see the pdf-lib constraint), and the **reset guard** (`assertPracticeDatabase`, an UN-memoized in-request re-check that is the load-bearing §5.3 refusal). **`SetupState` is a second by-construction singleton** (`id='singleton'` CHECK, the `BillingConfig` precedent; added to `AuditableModel` + `SNAPSHOT_INCLUDE`) holding only the two non-derivable first-run facts (`numbersConfirmedAt`, `checklistDismissedAt`) — everything else on the setup checklist is a live signal (`install-readiness.ts`, incl. the §5.7 admin-password-still-`admin` check). **`reseedSingletons` (`practice-seed.ts`)** restores the singletons + the eight Standard templates from `defaultConfigFor`, reused by both `truncateAll` (tests) and the practice reset (`practice-reset.ts`: truncate → singletons FIRST → `seedDemoSlice`, deliberately non-atomic behind the db-identity pre-check). **The order-entry gate** blocks `createOrder` until company identity AND a chart of accounts are configured (`order-entry-readiness.ts`), evaluated as a **pre-transaction read at the single `createOrder` chokepoint** — before the Serializable save, so a concurrent config edit is never a no-retry abort; the demo seed satisfies it, and the vitest harness seeds it **opt-in per order-creating suite** (`seedOrderGatePrereqs`), never in global `truncateAll` (which would red the pristine-default suites and contaminate the reset).

**Backups bridge the app and the nightly container through one shared folder (Phase 8C).** `BACKUP_DIR`
(container `/backups`, host `./backups`) is a **deploy value read by both writers**, never a runtime
`Setting` — the nightly container cannot honor a live change. `src/server/backup-paths.ts` is a **pure
leaf** (no fs, no db) and the ONLY way a filename becomes a path: `archivePath` refuses any name failing
the strict archive regex, which is what makes escaping the folder impossible — the deploy-set directory
cannot be "confined to a root" because it *is* the root. `pg_dump` is spawned **via argv, never a shell
string**, dumped to a temp file and checked for a non-zero size before it is gzipped into place (an empty
archive is never written). **`lastSuccessAt` is DERIVED from the newest integrity-passing archive, not
stored** — the archive is the evidence — which is what lets `backup-status.json` be a single un-merged
overwrite that `sh` can write. The two writers **never share a filename** (`erp_<stamp>` vs
`erp_manual_<stamp>_<rand>`), so no cross-process lock exists or is needed; both match the script's one
`-mtime +30` prune. The indicator is green ONLY on a recent integrity-passing archive **and** a clean last
run **and** a readable status file — **absence is failure**, so a missing status file reads red. One
deliberate exception (#132): retention health rides a **shell-only sidecar** (`retention-status.json`,
written every nightly run that reaches the prune, never by the Node manual path — which is what keeps a
"Back up now" from clearing a standing retention failure), and the sidecar's **absence contributes
nothing** — the main status file's absence rule already covers never-ran, and the sidecar self-refreshes
nightly. Backups
are **production-only**: `assertNotPracticeDatabase` (the `assertPracticeDatabase` mirror in
`practice-mode.ts`) refuses the routes, and compose denies `app-practice` both the env and the mount. The
suite must **never shell out to a host `pg_dump`** — CI's major is older than the server and pg_dump
refuses a newer server, so `runBackupNow` takes an injectable dump command (a parameter, not an env var).

## Constraints that will bite you

- **Client components must not import from `src/server/**`** — it drags `node:async_hooks` and Prisma into the browser bundle. Shared constants go in `src/lib/` (`permission-constants.ts` is the precedent).
- **`src/proxy.ts` runs on the Edge runtime and cannot reach the database.** (Next 16 renamed the `middleware` file convention to `proxy` — same execution model and same `config.matcher`, only the file and exported function names changed.) It is a cookie-*presence* redirect only, and it deliberately re-declares `SESSION_COOKIE` instead of importing it, because importing from `@/server/http` would pull Prisma into Edge. **THREE sites derive it from the same `SESSION_COOKIE_NAME` env var** — `@/server/http`, `src/proxy.ts` and `e2e/lib/warmup.mjs` — so only the fallback literal is duplicated; keep them in sync by hand. Extracting a `src/lib/` leaf would dissolve the duplication four other modules cite as the precedent for their own re-declared literals, so the warm-up's copy is **verified at runtime instead**. Real authorization is `requireUser` + `mustCan` in every route.
- **Any server-rendered page that fetches data must call `requireUser` itself.** The proxy does not authorize it. Phase 1 pages sidestep this by being client components against guarded APIs.
- **Route handler tests must pass ctx**: `handler(request, { params: Promise.resolve({}) })`. The `Handler` type requires it — Next's ParamCheck rejects an optional ctx (true through 15 and 16).
- Tests share one database and call `truncateAll()` in `beforeEach`; `vitest.config.ts` sets `fileParallelism: false` to keep that safe. Don't parallelize them.
- **`StoredDocument`'s kind→owner rule is a hand-written DB `CHECK`, not schema syntax.** Prisma's schema language has no check constraints, so `StoredDocument_kind_owner_check` is created in `prisma/migrations/20260804122700_certs_and_shipping/migration.sql` and **re-stated whole** each time the enum widens — the current definition is `prisma/migrations/20260810120100_quoting/migration.sql`, and **the schema's `StoredDocument` comment names whichever migration is current; trust it over this sentence**, which had gone stale by two widenings when #236 caught it (TRAVELER needs `orderId`; SHIPPER needs `shipperId` with `orderId` as an optional sub-scope — which order's ticket, null = the whole set — deliberately looser, do not "tighten" it; BOL needs `shipperId` alone; CERT needs `certId` alone; INVOICE and CREDIT need `invoiceId` alone; STATEMENT needs `customerId` alone; QUOTE needs `quoteId` alone — and every arm also asserts the columns it does NOT own are null). Adding a `DocumentKind` means a new migration DROPping and re-ADDing the CHECK **and** the `DocumentOwner` union + `AREA_FOR_KIND` in `src/server/documents.ts`; keep schema comment and SQL in step by hand. **The `ADD VALUE`s go in their own, earlier migration directory** — Postgres refuses to use a new enum value in the transaction that added it, and `migrate deploy` runs one directory per transaction (`20260804122600_document_kind_values`, `20260806221400_document_kind_invoice_values`, `20260808230000_document_kind_statement_value`, `20260810120000_quote_enum_values`).
- **`BillingConfig` is a one-row table by construction** — `CHECK ("id" = 'singleton')`, same migration and same style, with the row itself seeded by that migration so `getBillingConfig` is a plain `findFirst` and never a lazy create (P5A spec §4.5). `truncateAll()` (`tests/helpers/db.ts`) re-seeds it after the TRUNCATE for exactly that reason; don't drop that line.
- **npm ≥ 11.19 blocks dependency install scripts, and `package.json`'s `allowScripts` is what unblocks them.** Without it a plain `npm install` on a fresh clone *succeeds* while silently skipping `@prisma/engines`' postinstall — no query engine, so the first `prisma generate` or `tsc` fails somewhere unrelated — plus `argon2`, `esbuild`, `prisma` and `unrs-resolver`. The only signal is a `npm warn install-scripts` block at the end of an otherwise-green install, easy to scroll past. The five entries are **version-pinned** (npm's default), so a dependency bump un-approves that package and the skip returns: after any bump, `npm install-scripts ls` and re-approve with `npm install-scripts approve <pkg>`. Do not hand-edit the field, and do not "fix" a broken install with `--allow-scripts` — npm refuses that flag for project-scoped installs and points here.
- **Run everything on the Node in `.nvmrc` (26), because on an older Node the protection above does not exist.** npm 10 — what Node 22 ships — does not know the `allowScripts` field at all: it neither honours it nor warns, so an install there silently runs *every* dependency install script and the review gate is simply absent, while an install that SHOULD have been blocked looks identical to one that was allowed. The failure is quiet in both directions, which is what makes it worth a line here. It bit this repo for real on 2026-09-03, when a crashed session came back on nvm's `default` alias (then `22`) and the gates were briefly run on the wrong runtime. `.nvmrc` lives at the repo root — nvm walks upward, so `nvm use` finds it from `erp/` too — and **`ci.yml`'s two `setup-node` steps read `node-version-file: .nvmrc`**, so the file is the single source of truth rather than a comment that can drift from CI. `package.json`'s `engines.node` (`>=26`) states the same floor for anyone not using nvm. If `node -v` disagrees with `.nvmrc`, fix that before trusting any gate result.
- **`npx prisma migrate dev` needs a TTY.** It refuses outright in a non-interactive shell — including a Claude Code session driving Bash — with "the environment is non-interactive, which is not supported," and neither `CI=true` nor `--create-only` gets past it (it worked fine before Prisma 7). Without a TTY: `npx prisma migrate diff --from-config-datasource --to-schema=prisma/schema.prisma --script`, read the output in full, hand-write it into a new `prisma/migrations/<timestamp>_<name>/migration.sql`, then apply with the usual two `migrate deploy` calls. Every migration since Prisma 7 has been made this way (handoff §5.18); Phase 3 added four more with it.
- **Never `vi.spyOn` a Prisma model delegate** — `mockRestore()` does not put the original method back on this client, silently corrupting the shared `prisma` singleton for every later test in the run. Stub with plain property save/restore instead.
- **A Prisma `upsert` with an EMPTY `update: {}` is not atomic** — it compiles to a two-statement SELECT-then-INSERT, while a non-empty `update` compiles to a native `INSERT … ON CONFLICT DO UPDATE`. Two transactions creating the same row therefore both read "no row", both INSERT, and the loser dies on the unique/primary key. `allocateNumber` seeded its counter that way for five phases and only went red once it ran on hardware whose transactions genuinely overlap (fixed 2026-08-16 with a raw `INSERT … ON CONFLICT DO NOTHING`). **Where a row may be created concurrently, state the conflict clause in SQL** rather than resting on that ORM heuristic; never rely on `update: {}` for it. (That fix closed the P2002 insert race only; the Serializable abort on *every* allocation was #115, above.)
- **`renderPdf` output is not byte-deterministic across calls.** Tests that compare freshly rendered PDFs must pin content (e.g. the uncompressed `/Count N` page marker), never `Buffer.compare` two renders. Comparing STORED bytes on reprint is exact by design and stays `Buffer.compare`.
- **pdfmake's browser build wants a global `window` and will not run under Node.** Server-side PDF rendering (the traveler, `src/server/pdf/render.ts`) has to use pdfmake's low-level Node entry, the `PdfPrinter` constructor — **`pdfmake/js/Printer.js` since 0.3** (0.2's `pdfmake/src/printer.js` was removed; pdfmake ships no `exports` map, so this deep path is reachable but a future reorg can move it again — the #208 breakage, so keep render.ts its only importer). **0.3 also made `createPdfKitDocument` async and stopped accepting raw font Buffers**: `PdfPrinter` is now constructed with an in-process virtual filesystem and a no-op URL resolver, and fed font DESCRIPTORS that are vfs FILENAMES — Roboto decoded from the bundled `build/vfs_fonts.js`, the curated families from vendored `.ttf` — with the bytes served through the vfs at render time. The bytes are still read EAGERLY at module load (into `FONT_FILES`), so no file path is handed to pdfkit and nothing has to survive `output: "standalone"`'s file tracing. **`js/Printer.js` is CJS shaped `{ __esModule: true, default: PdfPrinter }`, so its default import is unwrapped with `.default ?? module`** — the e2e preflight loads `render.ts` transitively under **`tsx`** (Node's own CJS interop, which returns the namespace OBJECT, not the class), a THIRD module loader beyond vitest's Vite and the build's SWC; a bare `new PdfPrinter()` throws "not a constructor" there while passing both other loaders (the PR #210 CI catch — vitest/tsc/build were all green). That needs `next.config.ts`'s `serverExternalPackages: ["pdfmake", "bwip-js"]` alongside it: both are CJS with their own `require` graphs and megabytes of embedded font/barcode data the bundler would otherwise inline into every route that touches a document. **The curated non-Roboto font families (Phase 7 ruling 5) ship as vendored `.ttf` assets read at module load, kept in the standalone build by `outputFileTracingIncludes` — a corrupt font can't be uploaded, only vendored.**
- **`pdf-lib` is confined to `render.ts` — its only import site (grep-verified, keep it that way).** It has **two** sanctioned jobs: (1) MERGE the per-sheet-group PDFs Phase 7 renders (one `renderPdf` per traveler load / per shipping-ticket order, so each sheet group gets its OWN "Page N of M" and continuation header — pdfmake's callbacks only see whole-document page counts, and pdfmake cannot merge), and (2) the Phase 8B **practice watermark** post-stamp (`stampPractice`, keyed off `practiceMode()`, a true no-op short-circuit in production so renders stay byte-golden and reprints byte-exact; both `renderPdf` and `renderSheetGroups` funnel through it exactly once — the latter stamps the MERGED bytes, its per-group renders using the unstamped `renderPdfCore`). Definitions stay pure JSON; the footer/continuation-header specs are declarative data and the pdfmake/pdf-lib callbacks live only inside `render.ts`. Do not reach for `pdf-lib` from a builder or a service.

## Working conventions

TDD per task: failing test → implement → pass → commit. **An assertion about a guard is only
proven by MUTATION — delete the guard, watch the test red.** Vacuous and overclaiming assertions
are this repo's most-refiled defect class (#233 was instances 7–10), and they are invisible to a
green run by definition: a test whose subject 403s for two different reasons, or whose
`rejects.toThrow()` accepts any throw, passes exactly as loudly with the thing it names deleted.
The same rule covers COMMENTS that state a guarantee — #233's own three review rounds each fixed a
false claim and left or introduced another, every one of them found by checking the claim against
the code that produces it rather than by re-reading the prose. Conventional commit messages, with **no attribution trailer on individual commits** — owner's instruction, 2026-08-01. Every branch is squash-merged, so a per-commit `Co-Authored-By` / `Claude-Session` line gets concatenated N times into one squash message. Attribution goes in the **PR body**, where the squash preserves it exactly once. (Commits before 2026-08-01 carry the trailer; that is history, not the convention.)

**`main` is PROTECTED — everything goes through a PR, including a docs-only close-out.** The rules require a pull request and a passing `ci` check. A privileged account can push straight through, and GitHub then prints `Bypassed rule violations for refs/heads/main` — which is a report of a mistake, not a permission. **Close-outs are the trap**, because the close-out commits from earlier phases sit directly on `main` and read as precedent; they predate the rule. Branch, PR, merge — the same as any other change. If a bypassing push has already landed, **do not force-push `main` to tidy it away**: rewriting a pushed default branch is worse than the violation, and the honest fix is to leave the commit and route the next one properly.

The Phase 1 process is worth keeping: a fresh subagent per task, an independent spec-and-quality review of each task, fix rounds until approved, then a final whole-branch review before merge. Those per-task reviews caught real bugs the plan itself contained — a plaintext password in an audit payload, a `__proto__` registry crash, silent empty backups. The review loop is not ceremony.

**When to stop reviewing** (owner ruling, 2026-08-06, after Phase 4's seventh round). Review of review-fixes converges slowly — roughly half the findings in a late round are in code written for the previous round — and an LLM reviewer has no natural zero: severity converges, count never does. So from round 6 onward, findings are triaged to issues **unless they are correctness, concurrency, or data-integrity defects**. Do not read a non-empty round 7 as "not ready to merge."

**The execution record goes in `docs/execution/<date>-<phase>/`, and gets committed on the first task — not at the end.** Task briefs, implementer reports, reviewer verdicts and the progress ledger are the only account of *why* each task landed as it did, and none of it is reproducible from source. They used to live in `.superpowers/sdd/`, whose `.gitignore` is owned and rewritten by the SDD skill machinery: it has been clobbered back to a bare `*` repeatedly — twice across sessions and once *within* one — which hides every **untracked** file beneath it from `git status` and `git add`. That is how Phase 3's record was lost and how Phase 5A's nearly was. Two facts drive the rule: git applies ignore rules **only to untracked paths** (so a committed file is permanently immune, and the whole exposure window is "created but not yet committed"), and a nested `.gitignore` always beats the root one, so the root's `!.superpowers/sdd/` cannot rescue it. Committing early closes the window; `docs/execution/` keeps it closed. The `review-*.diff` packages stay in `.superpowers/sdd/` and stay ignored — they regenerate from two commits already in history. Historical phase ledgers stay where they are; they are already committed, hence already immune.

**Run `npm run test:e2e` whenever a change touches any UI, function, or flow** — even incidentally, and even when the flow isn't what you were fixing (owner instruction, 2026-08-06). Server-side fixes routinely alter behavior the Playwright flows exercise (warnings, headers, guards) that the unit gates never see. It needs the dev server and the DEV database (`erp`, not `erp_test`).

**CI runs it too, as a THIRD parallel job (`.github/workflows/ci.yml`, #167b, 2026-08-22) — before that it had never run in CI once.** It is the workflow's critical path, not free wall clock; the decision stands because the alternative on offer was no E2E gate at all. Five things in it are load-bearing and easy to undo, each with its own reasoning at the code. The database starts **once, before the suite, and no container is touched during the run** — a container start/stop is a host network-config change, #184's cause, so a mid-run `docker` step or a restarting service container reintroduces the flake deliberately. The **PostgreSQL client major matches `docker-compose.yml`'s `postgres:` tag AND wins the PATH lookup the app's own `spawn` performs** — the `backups` flow spawns a real `pg_dump`, which refuses a newer server, and installing the package is not by itself enough to be the binary that answers. The warm-up's **aggregate budget is raised at job level**, its dev-box default being tight enough on a slower machine to REFUSE the whole run rather than fail a flow. A **`RETRIED` flow warns rather than reds, still provisionally** (#190): the two surfaces the retry gate reads — the `<flow>__attempt-N` artifact dir and the `  RETRIED ` verdict line — are now `attemptDir`/`resultsLine` leaves pinned in `tests/e2e-harness.test.ts`, and the measurement is recorded (0 retries across the first e2e-job runs, but below the ~20-run clean-baseline bar), so the one-line `exit 0`→`exit 1` flip stays deferred until that baseline accrues. And the suite **STEP's timeout sits inside the JOB's** (`job ≥ setup + suite + retry-check + upload`) — raise one and the other must move, or the job cap silently becomes the real one. The reason is not that a cancelled job skips its remaining steps (`always()` steps ARE evaluated in the cancellation window): a JOB timeout CANCELS the job, and a cancelled job's step `outcome` is `cancelled`, not `failure`, so the upload never fires — which is also why it keys on the suite STEP's outcome rather than a bare `failure()`. Branch protection still requires only `ci`, so this runs on every PR but does not yet BLOCK a merge. Every number behind it is in HANDOFF §5a, dated.

**The harness warms, logs and CLASSIFIES (#184).** Before flow 1 it GETs every `src/app` route once and throws the answers away — enumerated from the filesystem, never a hand-list (`e2e/lib/warmup.mjs`), cookie-less for API routes so `requireUser` 401s before anything is parsed, and with a deliberately-invalid session cookie for pages, or the cookie-*presence* proxy 307s them all to `/login` and compiles nothing. That phase has an aggregate budget and **four** refusals (`warmupRefusal`): routes never issued, NO route enumerated at all, most requests failed, most PAGES redirected to `/login`. It writes the dev server's output to `e2e-artifacts/dev-server.log` on **every** run and **rotates** the previous run's artifacts to `e2e-artifacts-prev/` rather than deleting them — **after** the cheap refusals, since a refusal produces no evidence of its own and rotating on one spends the single generation this keeps. Each failure reports as **network-level** (a `requestfailed` record, not the error text — the throw is usually an innocent-looking locator timeout) or **assertion**, with two hard rules in `e2e/lib/failure-classify.mjs`: a `node:assert` **`ERR_ASSERTION` overrides the network signal outright**, the netFailure list being flow-wide, so one recovered drop at step 3 can never launder a step-40 assertion into a green retry — which is why a flow assertion is written with `node:assert`, never `throw new Error` (#193) — and **`net::ERR_ABORTED` is excluded on BOTH sides**, evidence list and text regex, an aborted navigation being deterministic rather than transport. A network-level failure is retried **once and only when the flow has provably mutated nothing**: zero 2xx mutating responses, zero mutating requests with no response, zero out-of-band writes. **The counters see only requests issued from a PAGE** — a `page.request.*` APIRequestContext call emits no context event at all — so an out-of-band write goes through `ctx.lockRevision` or `ctx.apiMutate`, and the harness **refuses the run** on a raw mutating `page.request.*` in any swept suite source — reached by dot, bracket (`page["request"].post`), or an aliased/destructured receiver (`const req = page.request`), the literal-`request`-receiver blind spot #192 closed (a `res.request()` method call and a `page.request.get` read stay allowed). **Never make that retry blind**: flows create real orders through the real UI and `template-build-and-load` leaves a template three later flows consume, so re-running one that failed at step 40 repeats steps 1–39. A retried flow prints `RETRIED`, never `PASS`. **On the cause, claim only what was measured:** `net::ERR_NETWORK_CHANGED` is a HOST-level event — Chromium drops every in-flight request, `localhost` included, when the machine's network configuration changes, and each container start/stop is one — reproducible here, and the explanation for the one post-fix failure instrumented end to end. But **#184's own four runs predate that instrumentation and carry no such record, so attributing them is inference**; the cold-compile hypothesis is refuted on the numbers (HANDOFF §5a, dated). Don't run a container-churning workload beside the suite, and don't read that error as an app defect.

**The warm-up's real cost is MEMORY, it is measured, and the harness now prints it.** Compiling all 243 routes into one `next dev` peaks around **9 GB** — the suite's largest single resource cost, and close enough to a 16 GB CI runner's ceiling to matter. It is dominated by the FIRST page compiled (~4.6 GB: the root layout, shell and shared client graph, not that page specifically); the other 242 routes add ~5 GB between them. The E2E dev server therefore runs with **`--disable-source-maps`** (~900 MB and ~10% faster, measured), which is a flag on the E2E server alone — `npm run dev` is untouched, and the trade is poorer stack traces in `dev-server.log`, which no flow is diagnosed from. Two alternatives were measured and REJECTED, so do not re-derive them: **a Node heap cap does nothing at all** (Turbopack allocates natively, so `--max-old-space-size=3072` gave 9734 MB against an uncapped 9722 — never "fix" this by capping the heap), and `--webpack` buys 12% of the memory for **2.3× the wall clock**. Every run now logs `dev server peak RSS through warm-up`, reported and deliberately not enforced — the number is legitimately large and machine-dependent, so a threshold would either fire on honest runs or sit too high to mean anything, while a logged number is comparable across runs. It is a PEAK, and getting that right needs **both** halves of `devServerMemoryMeter`: a 500 ms poll of the process group, and `/proc/<pid>/status`'s `VmHWM` at the end, whichever is larger. Neither alone suffices — polling has gaps between samples, and `VmHWM` vanishes with the transient compile workers `next dev` spawns and reaps. Measured: an end-only sample read 9193 MB where the pair read 9662 MB, and over a 50-route slice a poll saw 8087 MB against `VmHWM`'s 8001 MB. Do not "simplify" it back to one reading. That line exists because a real regression hid in this blind spot: **`next@16.3.4` costs ~800 MB PER API ROUTE** where 16.2.12 costs single-digit MB, so the same warm-up blew past 12 GB after 58 of 243 routes — which presented as a killed CI runner and two dead desktop sessions, none of which named memory. That is why Next is held at 16.2.12 (HANDOFF §4).

## Environment notes (Fedora)

If Postgres init or the backup container hits `permission denied` on the `./db-init`, `./scripts/backup.sh`, or either `./backups` bind mount (`app`'s and `backup`'s — Phase 8C mounts it on both), append `:z` to those four mounts in `erp/docker-compose.yml`. Prefer SELinux labels over disabling SELinux. The named `dbdata` volume needs nothing. **Keep that conditional** — on Fedora 44 with SELinux Enforcing and Docker CE 29.7 the mounts came up clean and `:z` was not needed (2026-08-26), so adding it unconditionally would be cargo cult.

**Install the Postgres CLIENT only, never a `*-server` package.** A host `postgresql-<major>.service` binds `127.0.0.1:5432` — the exact address compose publishes `db` on — so `docker compose up -d db` cannot bind, and the symptom is a *password authentication* failure against a server that is not ours. Check `ss -ltnp 'sport = :5432'` before blaming credentials; `sudo systemctl disable --now postgresql-18` clears it. The 18.x client must stay: the E2E `backups` flow spawns a real `pg_dump` and its major must match the `postgres:` image tag.
