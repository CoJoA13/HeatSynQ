# Phase 2C-3 demo — Process Steps + Templates (2026-08-02)

A ten-minute walkthrough for the owner: what shipped, the seed state to run it against, the six
E2E flows with their screenshots, how to watch live, and what changes for daily use.

## What Phase 2C-3 delivered

A part now owns its own recipe: an ordered, revisioned list of Process Steps, each naming a
shared Process Step Code and carrying that part's own instruction text and typed field values
(NUMBER/TEXT/DATE/CHECKBOX, rendered per code). Revisions are immutable once locked — editing a
locked current revision cuts revision N+1 automatically, copying the locked content first so the
edit lands on the copy while the original stays byte-identical and readable forever. Templates are
shop-built blank skeletons (ordered step codes + boilerplate text, never values) that load onto a
part's working revision, replacing it with confirmation. Step Code deletion is blocked whenever any
part revision or template still uses the code, through a generalized version of the same
blocker-registry mechanism the rest of the app already uses for reference data — the refusal names
every part and template that's blocking it, links to each, and exports to Excel. New UI: the
Processes nav page (template list + detail), a Process steps designer on the part detail page, and
completion of the Step Codes admin page's delete/active/history backlog, and — from the final-review
fix wave — a matching discoverable-blocker panel on the field-def delete/type-change guard. All of
it is covered by 574 integration tests plus a six-flow Playwright harness that produces screenshots
and video for every flow, the owner-visible E2E deliverable the phase's design session called for.

## Seed state

Nothing beyond the standard seed: `npm run db:seed` (creates `admin`/`admin`; change the password
after first login, same as always). The E2E run below creates its own throwaway fixtures in the
dev database — a customer (`E2ECUST`), a part (`E2E-PART-1`), two step codes (`E2E-QNCH` with
Temperature/Passed fields, `E2E-WASH` with none), a decoy template, and a second, deliberately
restricted user (`e2e_restricted`, `parts.view` + `processes.view` only, no `processes.edit` or
`processes.create`) — and tears all of it back out afterward, on success, on a thrown error, or on
Ctrl-C mid-run. There is nothing to set up or clean up by hand.

## The six E2E flows

Run with `npm run test:e2e` from `erp/`. Screenshots and a `video.webm` per flow land in
`erp/e2e-artifacts/<flow>/` (gitignored — reviewed locally, not committed). The flows run in a
fixed order because state carries forward: the template and two steps `template-build-and-load`
creates are what `typed-fields`, `revision-cut`, and `blocked-code-delete` go on to use; the last
two run as the restricted user rather than admin.

### 1. `template-build-and-load` — builds a template, loads it onto a part
Builds a two-step template ("E2E Austemper") with boilerplate text on the Processes page, then
opens the fixture part (which has no steps yet) and uses Load Template on it. The click fires a
confirm dialog — *"Replace the current steps with this template's blank skeleton?"* — every time,
whether or not the part already has steps; confirming loads the two steps with their boilerplate
copied into each step's instruction and every typed field left blank (a template carries structure,
never values). This is also the part's first-ever step mutation, which is what lazily creates its
revision 1.

**Demonstrates:** owner ruling 1 — *Load Template onto a part replaces with confirmation.*

Artifacts: `erp/e2e-artifacts/template-build-and-load/01-logged-in.png`,
`02-template-created-in-list.png`, `03-template-two-steps-with-boilerplate.png`,
`04-part-before-load-template.png`, `05-template-loaded-onto-part.png`, `video.webm`.

### 2. `typed-fields` — typed values render and persist
On the now-loaded `E2E-QNCH` step, fills the NUMBER field (Temperature: `1550`) and checks the
CHECKBOX field (Passed), saves, reloads the page, and confirms both values read back from the
server into their typed inputs rather than just having round-tripped through client state.

**Demonstrates:** the typed value model underneath the phase (§4/§6) — and it's the setup for
flow 3 below, which proves those same values survive a revision cut unchanged.

Artifacts: `erp/e2e-artifacts/typed-fields/01-logged-in.png`, `02-before-fill.png`,
`03-filled-before-save.png`, `04-saved.png`, `05-persisted-after-reload.png`, `video.webm`.

### 3. `revision-cut` — locked revisions freeze, edits cut a new one
Locks the part's revision 1 (standing in for what Phase 3's order save will do, via the exported
`lockRevision`), confirming the UI now shows `Rev 1 · locked` with a "Locked revision — editing
will create a new revision" notice. Edits the step's instruction anyway — the save silently cuts
revision 2, the picker jumps to `Rev 2 · working` showing the edit, and switching back to Rev 1
shows the *original* instruction with the Temperature/Passed values from flow 2 unchanged, every
control disabled with "Superseded revision — read-only".

**Demonstrates:** owner ruling 3, the "values stay frozen" half — a locked revision's values never
change under any edit; only a new revision can hold a new value. (The other half of ruling 3,
renames propagating into historical renders because there are no denormalized display columns,
isn't exercised by any of these six flows — none of them renames a code or relabels a field — so
it isn't an E2E screenshot. It's proven instead by
`tests/part-process-steps.test.ts`'s `"a locked revision renders a renamed code and relabeled
field live, while its values stay frozen"`: it locks a revision holding code `HT-01`/"Austentize"
(typo) and field label "Temp", renames the code to `HT-01A`/"Austenitize" and relabels the field
to "Temperature"/unit "F" — both id-preserving edits — then re-reads that same locked revision and
asserts it now renders the corrected spelling and label/unit while the step's instruction and the
value string are byte-identical to before the rename.)

Plain-language version of the rule: you can keep editing a part's recipe freely until an order
locks that revision (Phase 3). After that, the next edit doesn't touch the locked one — it silently
starts Rev N+1 with a copy of everything, and your edit lands there. Nothing you did before the
lock ever changes again.

Artifacts: `erp/e2e-artifacts/revision-cut/01-logged-in.png`, `02-rev1-locked-current.png`,
`03-rev2-working-after-cut.png`, `04-rev1-readonly-unchanged.png`, `video.webm`.

### 4. `blocked-code-delete` — deletion blocked, blockers named, export works
Attempts to delete `E2E-QNCH` from the Step Codes admin page — the code still used by the fixture
part's current revision and by the template built in flow 1. The delete is refused: a panel reports
"2 record(s) use it," naming and linking both the part and the template (never a dead end), and the
blocker list's own Excel export link serves a real file.

**Demonstrates:** owner ruling 2 — *deletion blocked on ANY live use, with a discoverable blocker
panel and export* — and owner ruling 4, since the block runs through the registry's generalized
`BlockerTarget` axis: the same `findBlockers` mechanism that already covers GL accounts, materials,
and the rest of reference data now also covers a part-owned step and a template-owned step in one
undifferentiated list.

Artifacts: `erp/e2e-artifacts/blocked-code-delete/01-logged-in.png`,
`02-step-code-selected.png`, `03-blocked-delete-panel.png`, `04-panel-dismissed.png`,
`video.webm`.

### 5. `permission-gating` — a restricted user sees the designer, can't touch it
Logged in as `e2e_restricted` (holds `processes.view` but not `processes.edit`), opens the fixture
part. The Process steps designer renders in full (view is granted, so there's no denied-placeholder)
but every mutating control — instruction textarea, typed fields, Save/Remove/Move, Add step,
Load Template — is disabled, each with a tooltip reading "Requires processes.edit".

**Demonstrates:** disabled-not-hidden permission gating (§5.16 convention) applied to the new
section — not one of the five numbered owner rulings itself, but part of the same "owner-visible,
never a silent dead end" philosophy those rulings share, and one more flow contributing to owner
ruling 5's E2E deliverable.

Artifacts: `erp/e2e-artifacts/permission-gating/01-logged-in.png`,
`02-part-designer-visible-to-restricted-user.png`,
`03-mutating-controls-disabled-with-tooltips.png`, `video.webm`.

### 6. `processes-list` — the Processes nav page, still as the restricted user
Still `e2e_restricted`: opens `/processes`, confirms both the real template and a decoy template
are listed, types a search term that narrows the grid to just the matching one, clears it, confirms
the export link serves a real spreadsheet, and confirms Add is disabled with a tooltip naming
`processes.create`.

**Demonstrates:** the Processes list page's standard conventions (search-as-you-type, export,
create gating) — again feeding owner ruling 5, the E2E deliverable itself, rather than one of the
other four.

Artifacts: `erp/e2e-artifacts/processes-list/01-logged-in.png`, `02-list-before-search.png`,
`03-search-narrowed.png`, `04-add-disabled-for-restricted-user.png`, `video.webm`.

## Watching it live

Two ways to see this running rather than just reading screenshots afterward:

- **Headed Playwright, watch the bundled Chromium click through it:**
  `HEADED=1 npm run test:e2e` from `erp/` — same six flows, same fixtures and cleanup, just a
  visible browser window instead of headless. This is the portable option; it needs nothing beyond
  what the repo already installs.
- **Chrome DevTools MCP, driven interactively in your own browser.** As of 2026-08-01 the Chrome
  extension is installed on this machine and the MCP server connects — the design spec's §12.2
  offers this as the second lane precisely so review rounds and this demo can click through the
  actual UI live, not just replay a recorded flow. Ask for a specific flow (e.g. "load a template
  onto a part and confirm the replace dialog") and it'll be driven in a real, visible Chrome window.

## What changed for daily use

- **Processes**, a new left-nav entry (visible to anyone holding `processes.view`), lists and
  manages Templates: search, sort, active-only filter, Excel export, and a detail page per template
  for its ordered steps and boilerplate text.
- **Part detail** gained a **Process steps** section between Custom fields and History: the
  revision picker (defaults to current, badge shows `Rev N · working` or `Rev N · locked`), the
  ordered step list with each step's typed fields, add/remove/reorder, and Load Template. Historical
  revisions render read-only; the current revision, once locked, warns before an edit that it will
  cut a new one.
- **Admin → Step codes** closed out its backlog: Delete now works (blocked-with-blockers per above),
  there's an Active toggle, and a History panel — all three were previously missing even though the
  API already supported them.
- **Admin → Step codes, field-level:** a field definition's delete/type-change guard got the same
  discoverable-blocker treatment. A field def whose only step values live under soft-deleted parts
  (or locked historical revisions) can never be deleted or type-changed — the panel now names those
  parts (with "(deleted)" markers for the soft-deleted ones); the escape is to relabel or re-unit
  the field, or leave it in place. That is deliberate, not a bug: `ProcessStepFieldDef` has no
  soft-delete of its own, so removing it is a genuine hard delete against
  `PartProcessStepValue.fieldDefId`'s `ON DELETE RESTRICT` FK, and Postgres refuses it outright no
  matter how the referencing part or revision got there.
- **Admin → Step codes, field order** (Codex fix wave): each field-def row gained up/down controls.
  That order is the order the fields are asked for on a process step and printed on the traveler,
  and spec §6 listed reorder alongside add/edit/delete — it was the one row operation never built.
  Without it a field's position was fixed for good once it recorded a value, since remove-and-re-add
  is exactly what the guard above refuses.
- **Locked revisions are now genuinely frozen against a concurrent order save** (second Codex
  round): `workingRevision` claims the current revision with `SELECT … FOR UPDATE` before reading
  `lockedAt`. Serializable isolation alone was not enough — Postgres only guarantees serializability
  among transactions that are *all* Serializable, and Phase 3's order save is documented to call
  `lockRevision` inside the order's own default-isolation transaction. Before this, an editor's save
  could read "unlocked", let the lock commit, and still write to the locked revision. A save that
  now loses the race either cuts N+1 or comes back as a 409 asking for a retry.
- **Part detail → Process steps, clearing a checkbox** (Codex fix wave): a step's CHECKBOX field
  gained the same `clear` action the part custom-fields checkbox already had. A checkbox alone can
  only ever stage "true" or "false" once touched, and "false" is a recorded value — enough to block
  its own field def's delete and type change, with no way back to unset.
