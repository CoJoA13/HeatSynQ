# Phase 3 demo — Orders & Loads (2026-08-03)

A walkthrough for the owner: what shipped across the 17 tasks of Phase 3, the four new E2E flows
with their screenshots, how to watch it live, what changed for daily use, and a short list of
implementation calls worth a second look before this merges.

## What Phase 3 delivered

An order is now a first-class thing in the ERP, not just a schema on paper. Keying a customer, a
lead part, and however many rider lines produces one order that **locks the lead part's process
revision at the moment you save it** — the recipe that revision describes is frozen forever, even
if the part's recipe keeps changing afterward — and **auto-splits into loads** from the lead part's
per-load quantity/weight caps, exactly the way 1,000 pieces at 300/load becomes 300/300/300/100 on
the shop floor today. From there the order lives on a searchable board with a four-color traffic
light (driven by the customer's request date, business days only), can be edited, re-split,
linked to sibling orders, voided with a reason, and printed as a traveler — a real PDF, barcoded
with the order number, built from the same layout as the shop's current paper. Every one of those
is real, working software as of this branch, not a mockup.

Underneath that story: eleven new tables (`Order`, its lines/containers/serials/loads/charges,
attachments, drafts, saved views, and stored documents), the order save's locked-revision +
auto-split transaction, a loads editor with renumber and re-split, crash-safe autosaved drafts (a
closed tab or a dead browser loses nothing you typed), saved board views, a global search box that
finds an order, a part, or a customer from one input (and resolves an exact order number straight
to its page — built for a barcode scanner, spec §9), delete guards that now refuse to remove a part
or customer while a live order still references it, and the traveler itself: real PDFs rendered
server-side with `pdfmake` and a Code 128 barcode from `bwip-js`, one document per print action,
every print stored byte-for-byte so a reprint of an old traveler is never a different piece of
paper than what the shop actually worked from.

All of it is covered by **904 integration tests** and the ten-flow Playwright harness this task
adds four flows to — the owner-visible E2E deliverable the design session called for (spec §13).
Spec: `docs/superpowers/specs/2026-08-02-phase-3-orders-design.md`. Plan:
`docs/superpowers/plans/2026-08-02-phase-3-orders.md`.

## Seed state

Nothing beyond the standard seed: `npm run db:seed` (creates `admin`/`admin`; change the password
after first login). The E2E run below creates its own throwaway fixtures in the dev database — on
top of the process-suite's own customer/part/step-codes (unchanged from Phase 2C-3), Task 17 adds a
second customer (`E2EORDCUST`, on credit hold on purpose) with a lead part that already carries one
process step (so it can be ordered from the moment the harness starts) and a serialization-required
rider part — and tears all of it back out afterward, including the order itself and its stored
traveler, on success, on a thrown error, or on Ctrl-C mid-run. There is nothing to set up or clean
up by hand.

## The four new E2E flows

Run with `npm run test:e2e` from `erp/` — this now runs **ten** flows in sequence (the six from
Phase 2C-3, unchanged, plus these four). Screenshots and a `video.webm` per flow land in
`erp/e2e-artifacts/<flow>/` (gitignored — reviewed locally, not committed). The four order flows
share one order: `order-entry-full` creates it, and `board-search-scan`/`loads-after-print`/
`void-order` all operate on that same order, in that order — `void-order` runs last on purpose,
since voiding it leaves nothing for a later flow to build on.

### 7. `order-entry-full` — key a two-line order, through crash-safety and a warned save
Picks the credit-hold customer, a lead part (which shows its locked-at-save preview — "Rev 1 —
locks at save" — the moment it's picked), and adds a second, serialization-required rider line.
Types `R{001-005}` into the rider's serial field — the range shorthand spec §12.6 describes — and
watches it expand to five rows, clearing the "serialization required" warning live. Then, mid-flow,
it reloads the page on purpose: the "Draft from HH:MM — Resume / Discard" banner appears (the
autosave that ran while the form was being filled in), and Resume restores every field exactly,
proving a closed tab or a crash loses nothing typed so far. Saving surfaces the credit-hold
notice in a **save-with-warnings panel** — "Order #N saved." plus the warning listed, never raced
past by an immediate redirect — and clicking through lands on the hub showing the lead line's
**"Lead · Rev 1 locked"** badge: the recipe is frozen, on the record, from this point forward.

**Demonstrates:** the lead+rider order shape and the locked-revision guarantee (spec §3/§5.3), the
serial-range shorthand, autosaved-draft crash safety, and the save-with-warnings panel (the
"visibly, never silently" ruling — HANDOFF issue #4's heritage, applied here to credit hold).

### 8. `board-search-scan` — the board shows the order, global search lands on it
Confirms the order just created shows up on the board with its traffic light — the colored dot
beside the status word (spec §6) — then types the order's own number into the Shell's global
search box and presses Enter. The search resolves the exact number and navigates straight to the
order's hub, no click needed: this is the barcode-scan path a traveler's printed Code 128 exists to
feed (scan the paper, land on the order).

**Demonstrates:** the board's traffic light rendering for a live order, and global search's
exact-order-number short-circuit landing on the right record.

Artifacts: `erp/e2e-artifacts/board-search-scan/02-board-order-with-light.png`,
`03-search-landed-on-hub.png`, `video.webm`.

### 9. `loads-after-print` — print a traveler, then prove loads stay editable afterward
Prints the traveler from the hub's Documents section; the archive — empty a moment before — gains a
row with a working link to the stored PDF. This flow also fetches that PDF's own bytes (the same
session-authenticated request the link itself would make) and saves it alongside the screenshots as
`traveler.pdf`, which is what this doc's traveler screenshot below is rendered from. Then it edits
the order's one auto-split load — changing its weight — and saves: the edit succeeds (loads stay
editable after a print, by design, spec §5b), but the page now shows an amber warning, **"A
traveler has already printed — print a fresh one,"** because the stored PDF describes the loads as
they were at print time and this edit just made that description stale.

**Demonstrates:** traveler printing and the stored-documents archive (spec §8/§10), and the
loads-editable-after-print rule with its reprint nudge (owner ruling, spec §3/§5b) — the print
itself is never invalidated or blocked, only flagged as due for a fresh one.

Artifacts: `erp/e2e-artifacts/loads-after-print/02-hub-before-print.png`,
`03-documents-list-grown.png`, `04-amber-printed-warning.png`, `traveler.pdf`, `video.webm`.

**What the printed traveler actually looks like** (page 1 of `traveler.pdf`, opened with any PDF
viewer — same layout as the 2025 mockup in `docs/samples/`, section for section): the customer name
top-left, **Order Number N / Load 1** top-right above a scannable Code 128 barcode of the bare
order number; a part-lines table (quantity / part number-name-description / part weight / line
weight) for both the lead and the rider line; the order/load quantity-and-weight row, with the
load's own weight printed as a small grey line under "Load Quantity"; a **Process:** line left
intentionally blank (see the owner notes below) next to **Process ID: E2E-ORD-LEAD** (the lead
part's own number); the numbered process step with its instruction text and EQ#/OP/Date
handwriting boxes; and the RESULTS / TEMPERED RESULTS / FINAL INSPECTION PASS-FAIL footer with
Tested-By and OK-to-Ship signature lines. Every field on that page is real data this order actually
carries, not placeholder text.

### 10. `void-order` — void with a reason, the board hides it until you ask
Clicks "Void order" on the hub. A prompt asks for a reason — the exact copy: *"Void order #N?
Every control on this order becomes read-only. The order number is never reused and this cannot be
undone through the UI. Reason for voiding (recorded in the audit history):"* — and refuses to
proceed without one (spec §5.17: a delete that carries other records away, or frees something for
reuse, needs a reason; voiding is exactly that). Typing one and confirming shows the red
**"Voided — {reason}"** banner on the hub. Back on the board, the order is simply gone from the
default view — voided orders leave the board rather than showing greyed-out inline — and checking
**"Include voided"** brings it back, rendered as the plain word **"Voided"** with no colored light,
alongside the shop's own genuinely-voided orders from earlier development milestones (numbers are
never reused, so they all coexist on that toggle).

**Demonstrates:** void-with-required-reason (spec §5c/§5.17) and the board's include-voided toggle,
including that a voided row shows no traffic light — a light is a signal about a live order's
timeline, and a voided order has no timeline left to be urgent about.

Artifacts: `erp/e2e-artifacts/void-order/02-hub-before-void.png`, `03-hub-voided.png`,
`04-board-hides-voided.png`, `05-board-shows-with-include-voided.png`, `video.webm`.

## What changed for daily use

- **Orders** replaces the old "Orders" placeholder as the app's home page (`/`) — a searchable,
  filterable, sortable board: status, customer, date ranges, a free-text search box, and an
  include-voided toggle, with every column optionally hidden/reordered and remembered as a **saved
  view** (your own, or one marked default so it applies automatically next time you sign in).
- **New Order** is a single entry screen: pick a customer (credit-hold and standing order notes
  show immediately), pick a lead part (its process preview — steps and typed values — shows before
  you save, and a part with no process steps can't be the lead at all), add rider lines as needed,
  key serials one at a time or with a range like `EC{001-025}`, add containers and extra charges,
  and save. **If you navigate away or the browser dies mid-entry, nothing is lost** — the form
  autosaves every couple of seconds, and coming back offers to resume exactly where you left off.
- **The order hub** (click any board row, or land on it from search) is the one page for
  everything about an order after it's saved: overview and dates, lines (add/remove riders — the
  lead is fixed once saved), the locked process read-only, containers, serials, extra charges,
  loads (edit, add, remove, renumber, or re-split from scratch), notes, file attachments, the
  traveler-print archive, linking to sibling orders, and the full audit history.
- **Void** replaces editing a wrong order down to nothing: void it with a reason (kept forever in
  the audit trail) and key a fresh one. The order number is never reused.
- **Loads stay editable after a traveler prints** — the shop isn't locked out of fixing a load
  just because paper already went out — but the hub tells you plainly when a stored traveler no
  longer matches what's on screen, so nothing prints stale by accident.
- **Global search**, in the top bar on every page, finds an order, a part, or a customer from one
  box — type an exact order number and press Enter (what a barcode scanner does) to land on that
  order immediately, no click needed.
- **Deleting a part or a customer** is now refused, with the blocking orders named and linked,
  while any live order still references it — voided orders never block.
- A **request-days override** field is now on both the part and customer pages, for the rare part
  or account that needs a different turnaround than the shop-wide default.

## Owner notes — decisions you may want to revisit

Four judgment calls made during the build, each cheap to change if it doesn't match how you want
the shop to actually run:

1. **Global search's exact-order-number match works for any signed-in user, not just someone
   holding the Orders permission** (only the search's *list* of matching orders is filtered by
   permission — the bare "does order #1042 exist" check is not). Three of the planning documents
   for this feature anticipated exactly this reading, and it's the shape that makes scanning a
   traveler barcode useful for anyone standing at a workstation — but if you'd rather that lookup
   also required the Orders permission, it's a one-line change (`src/server/search.ts`).
2. **A save that returns a warning (credit hold today; a missing serialization notice would be
   another) stops on a "saved, but here's what you should know" panel instead of navigating you
   straight past it.** This is deliberate — the alternative is a warning nobody ever sees because
   the page has already moved on — but it does mean one extra click ("Go to order") on every
   credit-hold customer's order, every time.
3. **On the printed traveler:** the "Process:" line is left blank on purpose — the mockup prints a
   process *name* ("Austemper") that doesn't exist anywhere in today's data model, and every
   stand-in considered (the part's own name, a name built from step codes, the revision number)
   was judged more misleading than blank; naming a process is Phase 7's template designer's job. The
   "Process ID" line prints the **lead part's own number** rather than the masked family number the
   original mockup shows (e.g. `3541719C3`, not `35417XXC3`) — a sibling order names its actual
   lead part. And the load's weight now prints as a small grey line under "Load Quantity" — real
   data the current paper form doesn't have a place for, added rather than dropped.
4. **The one validation message with no line number:** if a part somehow reaches the save step with
   no process steps of its own, the error reads "This part has no process steps" — with no "Line 1"
   or "Lead line" in front of it, unlike every other rejection this build produces. That's the
   design spec's own literal required wording (it comes from a shared primitive that locks a part's
   revision without knowing which order line asked for it), not an oversight — but it is the one
   place a shop worker filling out an order wouldn't see which line the shoe fits, if they ever hit
   it through anything other than the entry page's own upfront check (which already stops you from
   picking such a part as the lead in the first place).
