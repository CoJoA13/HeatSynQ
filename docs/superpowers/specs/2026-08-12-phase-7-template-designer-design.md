## 1. Goal

Build spec §8's template designer: **the eight document types become data-driven templates — multiple per type, one default, per-customer assignment, versioned with a draft → publish cycle — edited in a structured visual editor with live preview against real records, and every default the phases 3–6 hardcoded becomes editable.** The promise this delivers is §1's second differentiator: more document customization than Visual Shop, whose own number here is zero (every VS layout is a vendor-compiled artifact).

Testable outcome (roadmap): **owner restyles the traveler/logo** — upload the shop logo, place it, rename a label, publish, print an order's traveler, and the stored PDF carries all of it.

## 2. Scope

**In:** the `DocumentTemplate`/`DocumentTemplateVersion`/`CustomerTemplateAssignment` model (§4); the per-type **template contract** (the "documented field list per document type" §8 calls for) as a single typed source of truth consumed by editor, validator, and builders (§5.3); draft → publish versioning with immutable published versions (§5.1); per-customer assignment with division → parent → type-default resolution (§5.2); the structured editor at full depth for **all eight types** — logo upload/placement, header block, section show/hide + reorder, field add/remove/reorder, **label overrides, number formats, date formats, column widths** (§3 rulings 1, 3), fonts from a curated bundled set (ruling 5), standing text blocks; live **preview against any real record, never archived** (§5.5); the render runtime's new primitives — **"Page N of M" for every type** (retiring the quote's code-footer exemption, delivering the shipping ticket's still-open ping — HANDOFF §7 item 5.1 — and improving on the invoice's owner-accepted "no page line" deviation from the 5A demo), per-sheet-group rendering with renderer-side continuation headers (#36), bounded traveler rendering (#43); **`Part.processName`** feeding the traveler's Process: slot and the invoice's create-time `processNames` snapshot (ruling 4); the four standing-text settings and the BOL's hardcoded legal text migrating into template content (§8's "edited in place"); seeded "Standard" templates per type whose published v1 reproduces today's layouts at the content level (the existing PDF content tests pass unchanged); `StoredDocument.templateVersionId` so every archived print names the version that produced it; the reserved `templates` permission area + `edit_templates` special action wired live (§7); fold-ins #87, #97, #98.

Font-file upload (ruling 5 — curated set only). New document types (the posting register stays hardcoded — it is a GL artifact on `GlExportBatch.register`, not one of §8's eight, and never a `StoredDocument`). Template import/export files. Automatic emailing (spec §3 non-goal). Per-part or per-order template assignment (per-customer only, per §8). Editing what a document *says* at print time (print-time one-off edits remain out per §7.4). ## 4. Data model

### 4.1 New tables

- **`DocumentTemplate`** — `docType TemplateDocType` (new 8-value DB enum: `TRAVELER`, `SHIPPER`, `MOS_SHIPPER`, `BOL`, `CERT`, `INVOICE`, `STATEMENT`, `QUOTE` — §8's list verbatim; `INVOICE` covers credits, `MOS_SHIPPER` is its own type per §8 even though one builder serves both ticket shapes today). `name String` (`@@unique([docType, name], where: raw("\"deletedAt\" IS NULL"))` — the partial-unique house rule). `isDefault Boolean @default(false)` (service-normalized: **exactly one live default per docType, always** — the seeded template starts as it; setting a new default clears the old inside one transaction; deleting the current default is refused until another is set). `publishedVersionId String?` → `DocumentTemplateVersion` (the pointer prints resolve; null only between create and first publish — and **a template with no published version can be neither the default nor assigned to a customer**, service-enforced under the template claim, so the resolution chain never dereferences null; the seeded templates are born published). `deletedAt`, timestamps. Relations: `versions`, `assignments`.
- **`DocumentTemplateVersion`** — `templateId`, `versionNumber Int` (**allocated when the draft opens**, under the template row's `FOR UPDATE` claim; `@@unique([templateId, versionNumber])`; a discarded draft's number is never reused, so the history may carry gaps — deliberate). `status String` (`DRAFT` → `PUBLISHED` | `DISCARDED`; published rows are **immutable** — service-enforced, no update path exists; **discard is a status flip, not a delete** — the row, its config, and its logo stay as append-only history, honoring §9's soft-deletes-only rule; there is no `deletedAt` and no delete path at all). `config Json` (the typed per-type template config, zod-validated `.strict()` against the type's contract on every write), `logoImage Bytes?` + `logoMimeType String?` (PNG/JPEG only, magic-byte sniffed — the #49 lesson; 512KB cap; carried per version so archived versions rerender-faithful and drafts can trial a logo; copied forward when a new draft opens — the per-version copy is an accepted storage trade: fidelity of history over deduplication, trivial at this shop's template-edit volume), `publishedAt DateTime?`, `publishedById → User?`, timestamps. **At most one `status = DRAFT` row per template** (service-enforced under the template claim).
- **`CustomerTemplateAssignment`** — `customerId → Customer`, `docType TemplateDocType`, `templateId → DocumentTemplate`, `deletedAt`, timestamps. `@@unique([customerId, docType], where: raw("\"deletedAt\" IS NULL"))`. Registered in the §5.14 blocker registry one way: deleting a template with live assignments is refused-and-named (with the Excel export); deleting a customer cascades its assignments (they are pure preferences — nothing else points at them).

## 5. Module behavior

### 5.1 Template lifecycle (draft → publish — ruling 2)

Create template (named, per type) → a DRAFT version opens with its `versionNumber` allocated under the template claim, pre-filled from the type's seeded default config → edit freely (audited, with `config` diffs) → preview at will (§5.5) → **publish** (`edit_templates` special + `templates.edit`): under a `SELECT … FOR UPDATE` claim of the template row, the draft flips to `PUBLISHED`, gets `publishedAt`/`publishedById`, and `publishedVersionId` moves to it — the same claim-then-act shape as `lockCurrentRevision`. Editing after publish opens a new draft copying the published config (and logo) forward. Reverting = "open draft from version N" then publish. Discarding a draft flips it to `DISCARDED` (audited; kept forever — §4.1).

**Draft concurrency:** the one live draft is shared, so draft saves carry an `updatedAt` precondition — a save against a draft someone else changed since it loaded is refused with a named 409, never silently merged (last-write-wins clobber is the notes-pair lesson).

**Publish vs print:** prints resolve `publishedVersionId` under their own claimed transactions, which are Serializable for every kind except the traveler (`printTraveler` runs at default isolation under its order claim — deliberately unchanged). The resolution is **correct at any isolation, by immutability, not by locking**: publish commits the pointer and the immutable published row atomically, so any committed pointer a print reads yields a complete published config; drafts can never print; and the stamped `templateVersionId` records exactly which version produced the paper. A print racing a publish may legitimately render with the previous published version — ruling 2's "from that moment" means commit order, not wall clock, and this spec records that as accepted-by-design. No print locks the template row and none needs to.

### 5.2 Resolution at print (ruling 7)

Every print already knows exactly one customer (shippers are single-customer by construction — the cross-customer save is rejected; invoices, certs, travelers, quotes, statements each carry one). Resolution per docType, inside the print's transaction: **nearest ancestor with a live assignment, starting at the document's customer and walking `parentId` toward the root → the type's default template** → that template's `publishedVersionId` (never null — §4.1's invariant). In the flat parent/division reality this is exactly ruling 7's "own → parent's → default"; deep trees behave sensibly (flagged §12). Invoice and credit prints both resolve `INVOICE`. **Shipment paper resolves by the shipment's order count**: a multi-order shipment's tickets — including the per-order ticket print of one of its orders — resolve `MOS_SHIPPER`; a single-order shipment's resolve `SHIPPER`; all paper from one shipment styles alike. Both types are seeded from the same current layout, free to diverge. The resolved version id is stamped onto the `StoredDocument` row.

### 5.3 The template contract (the §8 "documented field list per document type")

One TypeScript module per docType under `src/lib/template-contracts/` (client-safe — the editor imports it) declaring: the ordered **sections** (each with a stable key, display name, and whether hide/reorder is allowed), each section's **fields** (stable key, display name, default label, whether removable, whether it participates in a table column with a default width), the **text blocks** (key + default text), and the **format-knob surface** (which number/date formats apply where). This is the single source of truth: the zod config schema is generated from it, the editor renders from it, and each builder consumes a validated `TemplateConfig` typed by it. The contract's field keys map onto the existing `<Doc>Data` types — **a template can only re-arrange, re-label, restyle, show, or hide what the data layer already collects; it can never add a data source.** That inherits every snapshot rule for free: the invoice contract exposes only frozen snapshot columns (frozen-paper rule), the shipper/cert contracts expose the live-join-first-with-fallback fields as they exist, and the cert contract simply never lists internal no-print notes.

Config shape (per template version, all-JSON, zod `.strict()`): section visibility + order; per-field visibility, order, label override; per-column width override; logo placement (position slot from a fixed list + width) when a logo is present; font choices (base family from the curated set, per-role sizes: base/heading/small); number formats (negative style, price decimals 2–4, thousands separator) and one date format, from fixed pickers; text blocks (the type's standing texts, editable in place); page footer on/off ("Page N of M"). Builders keep their hardcoded values as `DEFAULT_CONFIG` constants — the TS constants are the canonical copy: they backfill any config key a stored version predates (config is versioned data; new knobs land with defaults so old versions keep rendering identically), `truncateAll()`'s re-seed is built from them, and a dedicated test asserts the seed migration's SQL literal deep-equals them per type (§9, §10 — the three-copies drift guard).

### 5.4 The builders become config-consumers

Each `build<Doc>Definition(data)` gains the second parameter `build<Doc>Definition(data, config)`. The builders remain the layout engine — code interpreting data — which is exactly §8's boundary: structured customization, not a painter. Purity is unchanged (config in, JSON out; round-trip tests extend to cover config-driven output, and the **quote's builder joins them** once §6.1's page primitive replaces its footer callback). The per-file duplicated formatters consolidate into config-driven formatting helpers per file (still per-file — the "no template at the mercy of another's edits" rule holds; what's shared is the contract module, which is pure declarations).

### 5.5 The editor and preview

One admin surface (under the existing admin area UI, gated on the `templates` area — §7): a list page (8 types × their templates, default starred, assignment counts) and the editor — structured panels from the contract (sections → fields → knobs → texts → logo → fonts) beside a **live preview** of the current draft rendered against a **real record the user picks** (order for traveler; shipment for ticket/BOL — the `MOS_SHIPPER` editor's picker filters to multi-order shipments and `SHIPPER`'s to single-order; cert; invoice **or credit** for `INVOICE` — a credit is the record that exercises ruling 3's negative-number formats; customer for statement; quote — pickers reuse the house search components). Preview is a POST that renders draft config + record to PDF bytes and streams them — **no `StoredDocument` row, no `printedAt`, no side effects**; the statement preview in particular **forces the finance-charge assessment off** (it is a write path on the real statement run) and takes `asOf`/`combineFamily` as explicit preview parameters defaulting to today/false. Preview is gated on `templates.view` **plus the same permission the type's print route requires** (`orders.view` / `shipping.view` / `certs.view` / `invoicing.view` / `receivables.view` for statements / `quotes.view`) — a preview exposes the real record's amounts, so it must never be a cheaper read than the print itself. The **customer page's assignment picker** needs template *names* only, and a user holding `customers.edit` without `templates.view` must not get a silently empty dropdown — the §5.15 rule — so template names (id/name/docType of live templates) are served by a narrow `requireUser`-only read alongside the picklists route; managing templates stays behind the `templates` area. §5.16 applies throughout: disabled controls name their missing permission; locked fields (§5.6) say why they're locked.

### 5.6 Locked elements (constraints templates cannot violate)

- **Traveler typed step fields**: §15's Step-fields ruling — "print in a fixed place and cannot be quietly omitted." The contract marks the steps section and its typed-field rendering non-removable; the editor shows them locked with the reason; the config validator refuses a config that hides them (defense in depth — the editor alone is not the enforcement). This supersedes §8's "steps on traveler" show/hide example (§11).
- **The traveler barcode**: §4/§8 — "barcode automatic." Same lock mechanics.
- **Cert internal notes**: not in the contract at all (nothing to lock — the field list never offers them).
- **Column widths** (ruling 3's guardrail): per-table width totals validated against the content width (564pt on LETTER); the ticket's tear-off strip is re-implemented flow-based (not `absolutePosition`) so width and row-count changes reflow instead of overlapping — closing HANDOFF §7 item 5.3 as a side effect.

### 5.7 `Part.processName` (ruling 4)

New optional Part field, plain text, entered on the part form (exported/pasted like its siblings). The traveler's Process: slot binds it live at render — blank prints nothing, exactly today's behavior. The invoice half is **create-time only**: when invoice assembly writes the existing `Invoice.processNames` snapshot, it uses `part.processName` when non-blank and today's priced-operation comma-join when blank; prints keep reading the snapshot unconditionally (frozen-paper rule — a later `processName` edit must never rewrite raised paper), and invoices raised before this phase are untouched. The field is presentation vocabulary, not process identity — nothing resolves or validates against it.

### 5.8 Fold-ins (ruling 6)

- **#36** — a traveler sheet overflowing LETTER repeats order number, load number, and barcode on continuation pages. Delivered by §6.1's **per-sheet-group rendering**: each load's sheet renders as its own `renderPdf` call whose continuation-header spec carries *that load's* static content, so the header is correct per load and never stamps a following load's first page.
- **#43** — `printTraveler` all-loads is bounded: per-load rendering (§6.1) bounds each render's memory; above a threshold the print refuses with a per-load instruction or batches, exact shape at plan time — either way the order-row lock is never held across an unbounded render.
- **#97** — `indicativeAmounts` asserts `ops.length === line.prices.length`.
- **#98** — `LINE_INPUT` gains the `.refine` allowing `sourceQuoteNumber` only with `priceSource === "QUOTE"`.
- **#87** — a shared safe-Content-Disposition helper (RFC 5987 encoding) used by `resolveDocumentFilename`'s consumers and the statement route; a hostile customer code can no longer crash a response after its PDF archived.

## 6. The render runtime

### 6.1 Page numbers and per-sheet-group rendering (closes the ticket's Page-N-of-M ping, improves on the invoice's accepted deviation, retires the quote exemption, powers #36)

Definitions stay pure JSON; the *renderer* (`render.ts`, already the only pdfmake-aware file) learns two declarative keys carried on the definition: a **footer spec** (`{ kind: "pageNofM", label?: string }` → the pdfmake footer callback is constructed renderer-side) and a **continuation-header spec** (static JSON content — text/images — repeated on every page after the first). Both are data; the callbacks exist only inside `render.ts`, the same indirection as the named table layouts. The quote's hand-written footer callback is deleted in favor of the primitive, and its builder gains the purity round-trip test it has been exempt from.

**Multi-sheet documents** (the whole-set shipping ticket: one sheet per order; the all-loads traveler: one sheet per load) need page numbers and continuation headers scoped to the **sheet group**, not the whole PDF — "Page 1 of 2" on a ticket means *that ticket's* pages, and pdfmake's callbacks only see whole-document page counts. The mechanism: **render each sheet group as its own `renderPdf` call** (each with its own footer/header spec) **and merge the resulting PDFs into the one stored document**. pdfmake cannot merge PDFs, so this adds **`pdf-lib`** (pure-JS, zero-dependency, no install scripts — consistent with the repo's supply-chain stance) as a production dependency used only inside `render.ts`'s module boundary — **a new-dependency call flagged in §12 for the owner**. Merge cost is per-print and bounded by the group count; #43's bound covers the pathological case. Single-sheet documents keep the single-render path unchanged.

### 6.2 Fonts (ruling 5)

Roboto's buffers come from pdfmake's own bundled vfs, and that path does **not** extend to new families — pdfmake carries no other font, and `serverExternalPackages` is what keeps its megabytes out of the route bundles. New families therefore ship as **`.ttf` assets vendored in the repo** (SIL-OFL-licensed families only), read into buffers once at module load from an app-root-resolved path, with **`outputFileTracingIncludes` added to `next.config.ts`** so they survive the standalone build — the same buffer-feeding into `PdfPrinter`'s font map as Roboto, different source. Candidate set for plan-time confirmation: Roboto (incumbent), Liberation Sans + Liberation Serif (Helvetica/Times metrics — the closest match to what VS paper looked like), Noto Serif, and a mono (Roboto Mono). Templates pick a base family per role from this list; an unknown family name in config fails validation, never falls through to a default silently.

### 6.3 Logos

Per-version bytes (§4.1), PNG/JPEG magic-byte sniffed on upload, size-capped (512KB), embedded via the existing `pngDataUri` path (JPEG equivalent added). Placement from fixed slots (header-left / header-center / header-right) plus a width; the header block reflows around it. No logo → today's text-only header.

## 7. Permissions, audit, and house rules

The **reserved seats go live**: the `templates` area (verified unused today — process-step templates gate on `processes`) gates the document-template surface — `view` reads templates and previews (plus the record-area gate, §5.5), `create`/`edit`/`delete` mutate templates and drafts; the **`edit_templates` special action** (also verified unused) gates the three acts that change what future paper looks like: **publish**, **set default**, and **customer assignment** — the `change_prices` pattern: area CRUD for the workspace, the named dangerous action for the consequential act. Routes follow the house shape (`requireUser` + `mustCan`/`mustDo` first line, zod, delegate); services own the rules; every mutation goes through the audit helpers (§4.2's registry additions — draft edits audit real config diffs). Template delete is **reasoned** (§5.17 classification: it retires a whole version history from view and frees a name for reuse) and **§5.14-blocked** when live customer assignments point at it, with the blocker list and Excel export; deleting the current default is refused outright until another default is set. **Removing a customer's template assignment needs no reason** (§5.17 classification: a pure preference — nothing rides along, nothing unique is freed). The E2E suite gains the roadmap's outcome as a flow: restyle traveler → publish → print → assert the stored PDF's content markers; `npm run test:e2e` runs on every UI-touching task per the standing rule.

## 8. Settings

Four keys retire (§4.2): the print-path readers are rewritten onto template config this phase, the settings-UI `TEXTAREA_KEYS` entries and the settings tests naming these keys retire in the same task, and the migration deletes the orphaned rows after copying their values into the seeded configs. No new settings: fonts, formats, and texts are all per-template; company identity stays where it is.

## 9. Migrations (the settled TTY-less shape, applied to BOTH databases)

1. **New-tables migration** — `TemplateDocType` enum, the three tables, `Part.processName`, `StoredDocument.templateVersionId` + FK + index. (No enum ADD VALUE anywhere, so no two-directory split this phase.)
2. **Seed migration** — one "Standard" `DocumentTemplate` per docType, `isDefault`, with a v1 `PUBLISHED` version whose `config` is the type's `DEFAULT_CONFIG` JSON **with the four standing-text values copied from the live `Setting` rows** (SQL subquery against `Setting`, falling back to the code default where the row is absent — a fresh install and an upgraded one both come out right; the orphaned rows are deleted after the copy), and the BOL's legal text seeded from the constants. The SQL literal is a hand-written copy of the TS `DEFAULT_CONFIG`; the §10 drift-guard test asserts the two stay identical. `truncateAll()` re-seeds these templates **from the TS constants** after TRUNCATE, the `BillingConfig` precedent — the print path may assume a default template always exists.

Hand-written via `migrate diff`, read in full, applied to dev + `erp_test`, `prisma generate` after.

## 10. Testing

TDD per task, real DB. The signature tests this phase must carry: **seeded-v1 golden compatibility** — every existing PDF content test passes unchanged against the seeded default templates (the conversion is provably invisible until an edit is published; content markers, never `Buffer.compare` of fresh renders); the **seed-vs-`DEFAULT_CONFIG` drift guard** (the migrated test DB's seeded config deep-equals the TS constant, per type); config zod strictness + locked-element refusal (a config hiding typed step fields or the barcode is rejected at the service, not just the editor); **never-published templates refused** as default or assignment (§4.1's invariant); **draft-never-prints** (a print concurrent with an open draft renders the published version — by immutability, §5.1, not by a shared claim); version immutability (no path updates a `PUBLISHED` row); the draft `updatedAt` precondition's named 409; resolution-chain unit tests (nearest-ancestor walk, soft-deleted assignments ignored, shipment-order-count type selection incl. the per-order-ticket case); `templateVersionId` stamped on every new `StoredDocument`; purity round-trips now including the quote; per-sheet-group numbering (a two-load traveler's second sheet restarts at "Page 1 of N", continuation header carries the right load); partial-unique sweep entries for the new tables; permission sweeps pick up the new routes automatically; the #36/#43/#87/#97/#98 regression tests; the E2E restyle flow (§7).
